# Фильтр статуса проекта в списке проектов — дизайн-спека

**Design tier:** 2 (правка существующего экрана)
**Экран:** `/projects` (список), затрагивает `ProjectRow` (карточка-строка)
**Источник бизнес-контекста:** `docs/superpowers/specs/2026-09-01-notifications-and-confirmations-design.md`
§3–4, §6 — **прочитан целиком**, решения владельца ниже не пересматриваются, а переводятся в
конкретную вёрстку.
**Референсы (текущий экран, до правки):** `docs/design/assets/project-status-filter/current-*.png`
(320¹/375/768/1024/1440 — см. §4)
**Тема:** только тёмная (`apps/web/index.html` жёстко `class="dark"`) — светлую не проектирую и не

## 0. Что уже устроено на экране (важно для §3 решения)

Прочитан `apps/web/app/routes/_authenticated/projects/index.tsx` и
`apps/web/app/components/projects/ProjectRow.tsx` целиком, а не по памяти. Три факта определяют
всю дальнейшую конструкцию:

1. **`/projects` уже RBAC-огорожен** (`useRoleGuard(['ADMIN','SENIOR','HR','ACCOUNTANT','JUNIOR'])`
   — в списке и на детальной странице). **`DROP` на этот экран не попадает вообще.** Значит
   подтверждение проекта дропом (§4 бизнес-спеки: «проект подтверждают оба — синьор и дроп») живёт
   **не на этом экране** — это отдельная задача (вероятно, экран «что от меня ждут», §8.3 бизнес-
   спеки, Tier 1). Эта спека покрывает только ADMIN- и SENIOR-сторону списка.
2. **У страницы уже есть переключатель состояния** — `SegmentedToggle` в режиме `variant="tabs"`,
   ADMIN-only, три значения `Все | Активные | Архив` (`currentTab: StatusTab`). Это ГОТОВЫЙ слот
   под новый фильтр — не нужно придумывать новое место на экране.
3. **Список рядов — не грид карточек, а построчный список** (`ProjectRow`, сетка колонок
   `3fr 1.4fr 1.4fr 1.2fr 1fr`: инфо-проект | синьор | джун | ставка/дата | статус-бейджи). Правый
   столбец уже несёт условную бейдж-логику (домен ИЛИ «В архиве») — это то место, куда встраивается
   новый статус.

## 1. Бриф

Проект теперь начинает жизнь **черновиком** и становится боевым только после подтверждения
синьором (и, отдельным экраном — дропом, вне этой спеки). Список проектов получает **фильтр по
статусу подтверждения** — новое измерение, ортогональное существующей архивности
(«архивность остаётся отдельным измерением», §4.2 бизнес-спеки — не смешивать «не подтверждён» и
«закончен»).

Три значения (дословно из задания):

- **Активные** — по умолчанию; ровно то, что видят все роли сегодня.
- **Ожидают подтверждения** — черновики; видят ADMIN (все) и подтверждающий SENIOR (только свои).
- **Отклонённые** — видит только ADMIN, с причиной отказа, до ручной уборки.

## 2. Решение: фильтр заменяет существующий тройной таб, а не добавляется рядом

**Что делаю.** Существующий `SegmentedToggle` `Все | Активные | Архив` становится
`Активные | Ожидают подтверждения | Отклонённые | Архив` (для ADMIN) /
`Активные | Ожидают подтверждения` (для SENIOR) / полностью скрыт (для HR/ACCOUNTANT/JUNIOR —
как и сегодня).

**Почему не второй, отдельный переключатель рядом.** Два таб-бара на одном экране, один из
которых тоже содержит пункт «Активные» с ДРУГИМ охватом, — путаница на ровном месте: пользователь
не может понять, какая из двух «Активных» вкладок сейчас перед ним. Один список — один
переключатель, это и есть буквальное прочтение владельческого «фильтр в существующем списке, а не
отдельный раздел» (§6 бизнес-спеки) — раздел один, и управляющий элемент тоже должен быть один.

**Почему уходит вкладка «Все».** «Все» сегодня означает «активные + архивные вместе» — то самое
смешивание фактов о проекте, которое бизнес-спека прямо запрещает распространять на новую ось
(«не смешивать `не подтверждён` и `закончен`», §4.2). Смешивать теперь пришлось бы уже ТРИ факта
(подтверждён / архивный / отклонён), и результат нечитаем. Явные вкладки лучше одной мутной.

**Почему «Архив» остаётся 4-й вкладкой, а не отдельным контролом.** Архивным может стать только
ранее ACTIVE-проект (черновик нельзя заархивировать, отклонённый — тоже не архивируется, он просто
лежит с причиной). Значит «Архив» не пересекается по смыслу с двумя новыми состояниями и спокойно
остаётся как есть — просто сдвигается на 4-ю позицию.

**Статус — A1 (решение зафиксировано, не эскалируется).** Обратимо в пределах одного PR (это
клиентский UI-выбор, не миграция и не деньги), не задевает RBAC саму по себе (только отражает уже
существующую владельческую RBAC-модель из бизнес-спеки), не публикуется наружу. Если ревью
владельца сочтёт иначе — правка тривиальна (вернуть «Все» пятой вкладкой).

### Видимость по ролям (из §0.1 + бизнес-спеки §3, §7.2)

| Роль                     | Вкладки                                                | Охват «Ожидают подтверждения»                   |
| ------------------------ | ------------------------------------------------------ | ----------------------------------------------- |
| ADMIN                    | Активные · Ожидают подтверждения · Отклонённые · Архив | Все черновики, у кого угодно на подтверждении   |
| SENIOR                   | Активные · Ожидают подтверждения                       | Только те, где подтверждающий — сам этот SENIOR |
| HR / ACCOUNTANT / JUNIOR | нет вкладок (как сегодня)                              | —                                               |
| DROP                     | экран недоступен (см. §0.1)                            | —                                               |

Компонент `SegmentedToggle` рендерится по условию `isAdmin || isSenior` (расширение сегодняшнего
`isAdmin &&`); список опций строится по роли, не хардкодится.

### Тип и параметр (для Coder — ориентир, не мандат реализации)

```ts
type ProjectStatusFilter = 'ACTIVE' | 'PENDING' | 'REJECTED' | 'ARCHIVED'
```

Рекомендация: заменить сегодняшний `projectsSearchSchema = z.object({ archived: z.coerce.boolean().optional() })`
на `z.object({ status: z.enum(['ACTIVE','PENDING','REJECTED','ARCHIVED']).optional() })`, по тому же
принципу, по какому сегодня `archived=true` живёт в URL (deep-link на «Архив» уже так работает) —
ADMIN должен мочь заслать коллеге прямую ссылку на очередь «Ожидают подтверждения». `ACTIVE` —
дефолт, в URL не отображается (как и сегодня). Миграция старого `?archived=true` на `?status=ARCHIVED`
— техническое решение Coder'а, не дизайн-вопрос; риск низкий (внутренний инструмент, внешних
букмарков на `?archived=` не существует).

Переключение вкладки продолжает дергать бэкенд заново (как сегодняшний `archivedQuery`), с тем же
`keepPreviousData` + `useTransition`, чтобы анимация золотой таблетки `SegmentedToggle` не рвалась
серединой рендера (это уже задокументированное поведение в коде, ut-32/ut-44 — просто расширяется
на новую ось, не переизобретается).

**Без счётчиков на вкладках.** У `vacancies/index.tsx` таб-фильтр показывает счётчик (`Черновики 3`)
— но там весь список приходит ОДНИМ запросом и считается на клиенте. Здесь бэкенд уже отдаёт КАЖДУЮ
вкладку отдельным запросом (RBAC-скоуп различается для ADMIN/SENIOR) — счётчик на невыбранной
вкладке потребовал бы отдельного агрегирующего эндпоинта. Не в этой Tier-2 правке; сегодняшние
`Активные | Архив` тоже без счётчиков — согласованность важнее.

### Новое (минимально, обосновано)

1. **`ProjectRow` — расширение status-branching** (не новый компонент, правка существующего).

2. **`STATUS_FILTER_LABELS` / `STATUS_FILTER_LABELS_MOBILE`** (константы в `constants.ts`, рядом с

## 5. Адаптив (320/375 · 768 · 1024/1280 · 1440/1920)

### Ключевое решение: переключатель (табы), не выпадающий список — на ВСЕХ классах устройств

**Обоснование.** У этой же страницы-семейства (`vacancies/index.tsx`) уже есть решённая ИДЕНТИЧНАЯ
задача: 4-опционный табличный фильтр статуса, который на <640px не помещается по ширине с полными
русскими подписями (задокументировано прямо в коде: «4 full-length labels... collide at <640px,
confirmed live»). Решение уже вживую проверено и смёржено: **два инстанса `SegmentedToggle` с
разными наборами опций, переключаемые CSS-классами `sm:hidden` / `hidden ... sm:grid`** — не смена
компонента (таб → селект), а смена **длины подписи**. Я переиспользую то же решение вместо изобретения
третьего варианта:

- Экономит решение (не нужно проектировать поведение нового типа контрола — фокус/клавиатура/скролл
  внутри `<Select>` уже как-то работают, но это другой набор паттернов a11y).
- Пользователь уже видел этот механизм на `/vacancies` — переключатель, который на телефоне просто
  чуть короче подписан, предсказуемее, чем «на одном экране фильтр — таб, на другом — дропдаун».
- 24×24 CSS px (WCAG SC 2.5.8) — таб с текстом `text-xs` внутри `rounded-md` кнопки размера `sm`
  (`px-2 py-1`) технически проходит и сегодня; но ниже (§8) — почему этого недостаточно для мобайла
  и что добавляется.

### Подписи (полные / сокращённые — по образцу `vacancies/index.tsx`)

| Значение | Desktop (`sm:` и выше) | Mobile (`<640px`)                   |
| -------- | ---------------------- | ----------------------------------- |
| ACTIVE   | Активные               | Активные                            |
| PENDING  | Ожидают подтверждения  | Ожид.                               |
| REJECTED | Отклонённые            | Откл.                               |
| ARCHIVED | Архив                  | Архив (без изменений, уже короткое) |

`Активные` (8 симв.) и `Архив` (5 симв.) на мобайле не сокращаются — уже помещаются (видно на
`current-375.png`: сегодняшние 3 таба спокойно умещаются в 343px). Сокращения нужны только двум
новым, длинным подписям.

### Per-class поведение

- **320/375 (мобайл).** Сайдбар уже сворачивается в гамбургер (существующее поведение, не трогаем).
  Таб-переключатель — `SegmentedToggle` с сокращёнными подписями, `w-full` (растягивается на всю
  ширину контента, как сегодняшний тройной таб на скриншоте). Тач-таргет — см. §8 (44px минимум,
  сегодняшний `size="sm"` инструмент этого НЕ даёт «из коробки», добавляется явно).
  **Известное существующее ограничение (не в скоупе этой правки, зафиксировано, чтобы не выглядело
  регрессией от неё):** `current-375.png` показывает, что сама строка `ProjectRow` (5-колоночный
  grid) на 320-375 уже сегодня схлопывается с наложением текста («СИНЬОРДЖУН» друг на друга). Новый
  бейдж статуса встраивается в ТУ ЖЕ правую колонку по тому же паттерну, что и сегодняшний «В архиве»
  — он не может быть хуже уже существующего сжатия, но и не чинит его. Это отдельная, более крупная
  задача (переверстать `ProjectRow` в мобильный card-stack) — вне рамок Tier-2 фильтра.
- **768 (планшет).** Полные подписи (≥640px), таб-бар помещается свободно (см. `current-768.png` —
  сегодняшний тройной таб не близок к переполнению даже с более длинными подписями).
- **1024/1280 (ноутбук) и 1440/1920 (большой).** Без изменений в раскладке — таб-бар уже там, где
  сегодня, просто с 4 (ADMIN) или 2 (SENIOR) пунктами вместо 3.

### Тач-таргеты

`SegmentedToggle` `size="sm"` даёт `px-2 py-1 text-xs` — фактическая высота кнопки на глаз по
скриншотам заметно ниже 44px (мобильный минимум по `responsive-design.md`, строже WCAG-минимума
24px). Для мобильного инстанса (`sm:hidden`-вариант) добавляется `className="[&>button]:min-h-11"`
на контейнер (Tailwind arbitrary-child-selector, без правки самого `SegmentedToggle`) — поднимает
каждую кнопку до 44px по высоте, не трогая desktop-инстанс. Это тот же класс проблемы, что уже был
у `vacancies-status-filter-mobile` — если там тоже не добавлено, тот же фикс стоит внести туда одной
строкой (вне скоупа этой задачи, но стоит записать в бэклог одной строкой на Coder-обзор).

## 7. Плашка «ждёт подтверждения: имя» на карточке — вид и место

**Место.** Та же правая колонка `ProjectRow`, что сегодня несёт бейдж домена/архива
(`ProjectRow.tsx:232-254`, `flex flex-col items-end gap-1`) — никакой новой колонки, никакого сдвига
грида. Черновик **открывается той же карточкой, что и активный** (буквально требование §6 бизнес-
спеки) — значит вся остальная строка (лого, название, синьор, джун, ставка/дата) рендерится
БЕЗ ИЗМЕНЕНИЙ, меняется только правая колонка.

**Вид (сверху вниз внутри той же колонки):**

```
┌───────────────────────────┐
│  ⏱ Ждёт подтверждения      │   ← Badge, variant="outline", amber (§3)
│  от Олексій Коваленко      │   ← caption, text-[11px] text-amber-300/80,
│                             │      truncate + title = полное имя(-а)
└───────────────────────────┘
```

- Бейдж — `<Badge variant="outline" className="border-amber-500/30 bg-amber-500/20 text-amber-300 text-[10px]">`
  с иконкой `Clock` (`h-3 w-3 mr-1`, тот же паттерн иконки-в-бейдже, что `invoice-card.tsx`), текст
  «Ждёт подтверждения» — заменяет сегодняшний бейдж домена на этой вкладке (домен проекта не несёт
  ценности, пока проект не подтверждён, а место в колонке ограничено).
- Подпись под бейджем — `от {имя}` при одном ожидаемом подтверждении. **Несколько ожидаемых
  подтверждений одновременно (по бизнес-спеке §4.1, «одно предложение — несколько строк, по строке
  на подтверждающего») на ЭТОМ экране физически не возникает** — SENIOR тут видит только строки, где
  подтверждающий = он сам (§0.1: DROP на этот экран не заходит), значит с точки зрения SENIOR всегда
  ровно один «ждущий» — он сам, и текст можно не показывать вовсе (бейдж без подписи в SENIOR-скоупе
  избыточен). Для **ADMIN**, который видит ЧУЖИЕ черновики, подпись показывает, чьего решения ждём:
  «от {имя синьора}» — если ожидается только синьор; если по данным одновременно не хватает и
  синьора, и дропа — «от {имя синьора} и дропа» (дроп на этом экране безымянный по дизайну, т.к.
  сама сущность DROP не масштабируется сюда осмысленно — карточка не про DROP-детали). Точная форма
  зависит от того, что реально отдаёт API (см. допущение в §9) — Coder уточняет по факту формы ответа.
- Точка-индикатор рядом с названием проекта (сегодня `bg-emerald-500`/`bg-muted-foreground/40`) —
  добавляется третье значение `bg-amber-500` для `status === 'DRAFT'`.
- Строка **НЕ затемняется** (`opacity-60`, как архив/отклонённые) — черновик требует внимания
  прямо сейчас, приглушать его неверно по смыслу. Вместо этого — тонкий акцент по всей карточке:
  `ring-1 ring-amber-500/20` на внешнем `div` строки (тот же приём, что `invoice-card.tsx:110` для
  «ожидается ваша подпись» — уже проверенный, не новый).

## 8. Причина отказа на отклонённом

Тот же принцип, что уже работает для `tx.rejectionReason` в финансах (`TransactionRow.tsx:661-670`)
— причина видна **прямо в строке списка**, без захода в карточку, потому что задача — «убрать
разногласия», а спрятанная за кликом причина работает хуже открытой.

```
┌───────────────────────────┐
│  ✕ Отклонено                │   ← Badge, variant="outline", destructive (§3)
│  «нет бюджета на Q3»       │   ← причина, text-[11px] text-destructive/90,
│                             │      truncate + title = полный текст
└───────────────────────────┘
```

- Бейдж — `<Badge variant="outline" className="border-destructive/30 bg-destructive/10 text-destructive text-[10px]">`,
  иконка `XCircle`, текст «Отклонено» — заменяет бейдж домена, аналогично §7.
- Причина — прямой текст под бейджем, `truncate` на ширину колонки + `title={reason}` (полный текст
  по наведению — паттерн `TransactionRow.tsx:666-669`).
- Точка-индикатор — `bg-destructive/60` (приглушённая, отличима от архивной `bg-muted-foreground/40`
  и от активной `bg-emerald-500` по оттенку и по соседнему тексту, не только по цвету — см. §9 про
  1.4.1).
- Строка **затемняется** (`opacity-60 hover:opacity-80`) — тот же класс, что архивная строка сегодня
  (`ProjectRow.tsx:69`): отклонённый проект — историческое состояние, ожидающее ручной уборки
  админом, не активный к действию элемент (в отличие от черновика).
- **Действие «предложить заново» — вне этой спеки.** Бизнес-спека (§3.3) явно даёт админу
  возможность предложить снова после отказа — но по конвенции этого экрана ВСЕ действия живут на
  детальной странице проекта, не на строке списка («ut-27 + ut-38: archive/unarchive... live on the
  project detail page header», прямо в коде `ProjectsPage`, комментарий в конце файла). Строка —
  только индикация; клик по ней (как и сегодня) ведёт на `$projectId`, где это действие и должно
  появиться — отдельная Tier 1/2 задача для детальной страницы, не часть этой.

## 9. Допущения (A1, записаны, не эскалируются)

**Фундамент согласований уже смёржен** (`feat(approvals): confirmations foundation — one record per
approver`, PR #624, позиция 3 из плана бизнес-спеки) — проверено чтением
`packages/shared/src/schemas/approvals.ts` и `apps/api/src/approvals/approvals.service.ts` напрямую,
а не по памяти о спеке. Ниже — допущения, заземлённые в этом реальном коде, а не изобретённые:

- **`Approval`-строка не несёт имени и роли** — только `approverUserId: string (uuid)`,
  `status: 'PENDING'|'APPROVED'|'REJECTED'`, `rejectionReason: string|null`, `subjectType`,
  `subjectId`. Значит подпись «от {имя}» (§7) на этапе позиций 4/5 плана потребует JOIN
  `approverUserId → users.displayName` — эта спека этого не решает (не её слой), только
  фиксирует, что колонка `ProjectRow` рассчитана на уже готовое имя в DTO, а не на сырой uuid.
  Роль подтверждающего (SENIOR vs DROP) на самой `Approval`-строке тоже не хранится
  (`subjectType`/`subjectId` — только про ЧТО подтверждается, не про роль подтверждающего) —
  вывод роли (для формулировки «от синьора» vs «и дропа», §7) ляжет на сопоставление
  `approverUserId` с `project.seniorId`/`project.dropId` при сборке DTO.
- **Агрегатный статус уже посчитан заранее** — `ApprovalsService.getStatus()` возвращает
  `'NONE' | 'PENDING' | 'APPROVED' | 'REJECTED'` (частичное согласие = `PENDING`, «отказ одного
  гасит всё» = `REJECTED`). Это готовая основа для `project.status`, которое эта спека
  предполагает как `'DRAFT' | 'ACTIVE' | 'REJECTED'` — вероятное сопоставление:
  `NONE|PENDING → DRAFT`, `APPROVED → ACTIVE`, `REJECTED → REJECTED`. Точное имя/форма поля на
  `ProjectDto` — решение Coder'а при реализации позиции 4 плана («Черновик проекта: статус,
  представление, страж»), не этой спеки.
- **`listPendingForApprover(approverUserId)`** уже существует и возвращает ВСЕ pending-строки
  подтверждающего по ЛЮБОМУ `subjectType` (не только проектам) — ровно тот метод, которым для
  SENIOR-скоупа вкладки «Ожидают подтверждения» естественно фильтровать `subjectType='PROJECT'`
  (значение `subjectType`, судя по коду, ещё не зарезервировано ни одним модулем — вводится тем,
  кто реализует позицию 4, тоже вне этой спеки).
- **`project.rejectionReason`** — из §4.2 бизнес-спеки («явное поле… причина отказа»); на уровне
  `Approval`-строки причина уже есть (`rejectionReason` на КОНКРЕТНОЙ отклонившей строке) — какое
  из двух полей проецируется в `ProjectDto.rejectionReason` (сырое из `Approval` или
  денормализованная копия на проекте) — снова реализационное решение, не дизайн-вопрос: вёрстка
  §8 ожидает одну строку текста, откуда бы она ни бралась.
- **Замена `?archived=` на `?status=` в URL-схеме** — техническое решение, не дизайн-требование;
  альтернатива (оставить `archived` булевым параметром рядом с новым `status`) тоже приемлема, если
  Coder сочтёт миграцию схемы рискованной для существующих ссылок.

## 10. A11y (WCAG 2.2 AA)

Проверено через skill `accessibility` (роли/live-region паттерн) — ниже применение к этому фильтру.

- **Роли.** `SegmentedToggle` уже рендерит `role="tablist"` + `role="tab"` + `aria-selected` в
  режиме `variant="tabs"` (используемом здесь) — ничего дополнительно навешивать не нужно, это
  ровно правильная семантика для «один выбор из статического набора вкладок, меняющих контент
  ниже».
- **Фокус.** `SegmentedToggle` уже даёт `focus-visible:ring-2 focus-visible:ring-ring
focus-visible:ring-offset-2` на каждой кнопке (SC 2.4.11) — не трогается.
- **Тач-таргет.** 44×44 CSS px на мобильном инстансе — см. §5 (явная правка, не полагаться на
  дефолтный `size="sm"`).
- **Цвет — не единственный носитель смысла (SC 1.4.1).** Каждый статус несёт ТРИ независимых
  сигнала, не один цвет: (1) текст бейджа — «Ждёт подтверждения» / «Отклонено», не просто цветная
  точка; (2) иконка — `Clock` vs `XCircle`, разная форма, различима и для пользователей с
  дальтонизмом; (3) для отклонённого — ещё и явный текст причины ниже. Точка-индикатор у названия —
  декоративное усиление ПОВЕРХ уже словесно объявленного статуса, не единственный носитель.
- **Объявление смены фильтра для скринридера (SC 4.1.3, status messages).** Смена самой вкладки
  озвучивается нативно через `aria-selected` на кнопке, получившей фокус/клик (уже работает,
  свойство `role="tab"`). Что НЕ озвучивается сегодня — результат: список ниже перерисовывается вне
  фокуса пользователя. Добавляется один `sr-only` параграф с `aria-live="polite"` рядом со списком
  (`aria-atomic="true"`, чтобы весь текст перечитывался целиком, а не по diff):

  ```tsx
  <p className="sr-only" aria-live="polite" aria-atomic="true">
    {STATUS_FILTER_LABELS[currentTab]}. Показано проектов: {filtered.length}.
  </p>
  ```

  Формулировка «Показано проектов: N» намеренно обходит русское согласование числительных
  (1 проект / 2 проекта / 5 проектов) — конструкция «показано X: N» грамматически верна при любом N
  без словаря склонений.

- **Бейджи в правой колонке** — не интерактивны (это статус, не кнопка), поэтому не требуют
  собственного тач-таргета отдельно от уже кликабельной всей строки (stretched-link на всю карточку
  уже покрывает переход на детальную страницу, см. `ProjectRow.tsx:96-106`).
- **Тема.** Только тёмная — контраст `amber-300 on bg-amber-500/20` и `destructive on bg-destructive/10`
  уже проверенные в проде пары (используются на этой же тёмной теме в `document-status-badge.tsx` /
  `TransactionRow.tsx` без отдельных находок по контрасту) — новых замеров не требуется, тональность
  идентична существующим местам применения.
