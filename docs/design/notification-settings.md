## 0. Что уже устроено (важно для конструкции ниже)

Прочитано напрямую, не по памяти:

1. **`UserProfileShell.tsx`** — вкладки объявлены в трёх местах, все три нужно тронуть при
   реализации (не дизайн-решение, но фиксирую здесь, чтобы Coder не собирал по крупицам):
   - `TAB_LABELS` (`Record<string, string>`) — подпись вкладки.
   - `SELF_ALLOWED_TABS` — константа, которой `mode === 'self'` фильтрует `permissions.tabs`
     backend'а. Для `mode === 'view'` фильтра нет вообще — `visibleTabs = permissions.tabs`
     напрямую (backend решает целиком).
   - Блок `{activeTab === '<tab>' && visibleTabs.includes('<tab>') && <XTab .../>}` в конце файла.
   - `packages/shared/src/schemas/view-permissions.ts` → `tabKeySchema` (Zod-enum) — нужно
     добавить `'notifications'`, иначе `permissions.tabs` не пройдёт парсинг.
   - `apps/web/app/routes/_authenticated/profile/index.tsx` → `searchSchema.tab` (Zod-enum) —
     то же самое для URL search-параметра.
2. **AC1 («нет вкладки в `view`, `?tab=notifications` → «Обзор»») получается бесплатно**, если
   backend для `mode === 'view'` профиля **никогда** не кладёт `'notifications'` в
   `permissions.tabs` (личные настройки канала — не то, что видит смотрящий). Тогда
   `visibleTabs.includes('notifications')` = false → `activeTab` откатывается на
   `visibleTabs[0] ?? 'overview'` тем же кодом, что уже обрабатывает любой недоступный tab.
   Это backend-контракт (7a или отдельный DTO-патч), не разметка — фиксирую как ожидание, не
   реализую.
3. **`Switch` (`role="switch"`) в `apps/web/app/components/ui/` НЕТ.** Проверено листингом
   каталога (36 файлов) — есть `segmented-toggle.tsx` (радиогруппа, не бинарный переключатель) и
   `radio-group.tsx`, но ни одного ARIA-`switch`. `@radix-ui/react-switch` тоже отсутствует в
   `apps/web/package.json` (11 `@radix-ui/*` пакетов, `react-switch` не входит). **Это единственный
   новый примитив, который требует эта задача** — см. §5.
4. **`Card` + `CardContent className="p-0"` + `<table>` внутри — уже установленный паттерн**
   (`FinanceTab.tsx:169-260`): карточка-контейнер, `overflow-x-auto` только внутри карточки, ручной
   `<table>`/`<thead>`/`<tbody>` (не обёртка `Table` из `ui/table.tsx`, которая сама добавляет
   `overflow-auto` — на вложенность с шапкой это не критично, но `FinanceTab` идёт ручной разметкой,
   и я следую тому же прецеденту ради консистентности с соседней вкладкой одного профиля).
5. **Ошибка + повтор — установленный паттерн** (`ContractPdfPreview.tsx:196-206`): иконка
   `AlertTriangle` приглушённого `text-destructive/60`, `text-sm text-muted-foreground` текст,
   `Button size="sm" variant="outline"` с текстом «Повторить».
6. **Тост об ошибке мутации — установленный паттерн** (`useEmployeeContract.ts`, 5 мутаций):

   ```
   toast.error(`Не удалось <действие>: ${msg}`)
   msg = err instanceof Error ? err.message : String(err)
   ```

   Значение `err.message` приходит уже готовым: перехватчик axios (`apps/web/app/lib/axios.ts:62`)
   прогоняет его через `getUserFacingErrorMessage` раньше, чем оно доходит до хука мутации — сам
   хук эту функцию второй раз не вызывает.

7. **`TypeIcon`** (`apps/web/app/components/layout/notifications-bell.tsx:57-84`) — per-type
   значок для всех десяти типов, актуальный (не тот, что на референс-скриншоте попапа, где
   заголовки — устаревший текст до COPY-раундов). Функция сегодня **не экспортирована** —
   рекомендую вынести в `apps/web/app/lib/notification-type-icon.tsx` и импортировать в оба места
   (попап + новая таблица), чтобы значок не разъезжался по двум копиям. Не мандаторно (deletion-тест:
   можно оставить как есть и продублировать 10-way switch — не критично для одной задачи), но
   дешевле сделать сразу.
8. **`NOTIFICATION_TITLES`** (`packages/shared/src/schemas/notification-registry.ts:92`) — ЕДИНЫЙ
   источник заголовков для всех десяти типов, уже прошёл несколько раундов `copy-reviewer`
   (см. комментарии `COPY-H-1`…`COPY-M-5` в файле). **Настройки обязаны импортировать именно эту
   карту**, не заводить вторую — тест AC2 сверяет строки напрямую.

## 2. Состав данных: группы, порядок, членство

Источник — `packages/shared/src/schemas/notification-registry.ts`. Группа не хранится в API-ответе
(в проектируемом контракте, §7) — **UI сам раскладывает по типу**, тем же принципом, каким уже
разложены константы реестра:

| Группа (заголовок в UI) | Членство (предикат по `type`)                                                | Типы (порядок — как в реестре)                                                 | `locked` |
| ----------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | -------- |
| **Требуют ответа**      | `ACTION_REQUIRED_NOTIFICATION_TYPES`                                         | `PROJECT_CONFIRM_REQUIRED`, `SHARE_CONFIRM_REQUIRED`, `DOCUMENT_SIGN_REQUIRED` | все три  |
| **Деньги**              | `INFORMING_NOTIFICATION_TYPES` где `type.startsWith('TRANSACTION_')`         | `TRANSACTION_ADDED`, `TRANSACTION_STATUS_CHANGED`                              | нет      |
| **Команда и проекты**   | остаток `INFORMING_NOTIFICATION_TYPES`                                       | `TEAM_MEMBER_ADDED`, `PROJECT_MEMBER_ADDED`, `TEAM_NEW_MEMBER`                 | нет      |
| **Для администратора**  | `ADMIN_NOTIFICATION_TYPES`, рендерится только если `viewer.role === 'ADMIN'` | `APPROVAL_CONFIRMED`, `APPROVAL_REJECTED`                                      | нет      |

**Почему предикат `startsWith('TRANSACTION_')`, а не срез массива по индексу.** Индекс совпадает
сегодня случайно (транзакционные типы стоят первыми двумя в `INFORMING_NOTIFICATION_TYPES`) — предикат
по имени типа не сломается, если реестр когда-нибудь переставит порядок или добавит одиннадцатый
тип между ними. Дешевле писать один раз правильно, чем чинить молчаливый дрейф позже.

**Группа «Для администратора» — условие видимости на UI, а НЕ то же самое, что список от бэкенда.**
Задание прямо говорит «список отдаёт бэкенд, UI не решает за него» — т.е. если бэкенд вернул
`APPROVAL_CONFIRMED`/`APPROVAL_REJECTED` в ответе (для не-ADMIN он их вернуть не должен по RBAC), UI
рендерит группу только при `viewer.role === 'ADMIN'` — двойная защита (бэкенд не отдаёт + UI не
показывает), а не полагание на одно из двух. Это же — предмет проверки `security-reviewer` (задание,
раздел «Обязательные гейты»): UI не должен быть единственной линией обороны, но не должен и
показывать лишнее, если бэкенд по ошибке отдаст.

**Неизвестный тип** (позиция та же, что AC2 позиции 6) — отдельная безымянная группа **в конце**
списка, без заголовка «Требуют ответа/Деньги/…», подписанная общим текстом (см. §9.3).

## 4. Компоненты

### Существующие (переиспользуются как есть)

- `Card` / `CardContent` — контейнер (§3).
- `Skeleton` — состояние загрузки.
- `Button` (`variant="outline"`, `size="sm"`) — «Повторить».
- `AnimatedTabs` — вкладка регистрируется в существующем перечне, компонент не меняется.
- `toast` (`sonner`) — успех/ошибка сохранения.
- `TypeIcon` (рекомендовано вынести в общий модуль, см. §0.7) — значок per-type.
- `NOTIFICATION_TITLES` (`@crm/shared`) — заголовки типов, один источник с попапом.

### Новое (минимально, обосновано)

1. **`Switch` (`apps/web/app/components/ui/switch.tsx`)** — стандартный shadcn/ui примитив поверх
   `@radix-ui/react-switch` (добавить зависимость: `pnpm --filter @crm/web add @radix-ui/react-switch`).
   Обоснование: задание требует `role="switch"` + `aria-checked` — это ARIA-семантика **бинарного**
   переключателя состояния, не радиогруппы (`SegmentedToggle`/`radio-group.tsx` кодируют «выбор
   одного из N», а не «вкл/выкл»). Использовать нативный Radix-примитив, а не самодельный `<button>`
   с ручными ARIA-атрибутами — Radix уже даёт правильную клавиатурную навигацию (`Space`/`Enter`),
   `data-state`, `aria-checked`, `aria-disabled` бесплатно. Стилизуется токенами из §3 — новый
   компонент, но НЕ новый визуальный язык (тот же `--primary`/`--input`/`--ring`, что и везде).
2. **`useNotificationPreferences()` / `useUpdateNotificationPreference()`** (хуки, зеркалят паттерн
   `use-notifications-api.ts`) — `GET/PUT /notifications/preferences`, см. §7 для контракта и
   поведения. Не UI-компонент, но часть контракта этой спеки.
3. **`NotificationSettingsTab.tsx`** (в `apps/web/app/components/user-profile/tabs/`, по образцу
   соседних `*Tab.tsx`) — сама вкладка: группировка (§2), рендер таблицы/стека (§6), состояния (§9).

**Явно НЕ вводится:** отдельный компонент под «мастер-переключатель всех писем сразу» — заданием не
запрошен, придумывать не буду (см. `codebase-design`: deletion-тест — добавь только то, что реально
нужно сейчас).

Ряд — `flex flex-col gap-1 p-4 border-b border-border/50` (карточка внутри той же `Card`, не
отдельные вложенные карточки — «карточка в карточке» запрещена `foundation.md` anti-patterns).
Заголовок ряда — `flex items-start justify-between gap-3`: слева иконка+название (`flex-1 min-w-0`,
`break-words`, НЕ `truncate` — длинные заголовки уже короткие ≤24 символов по COPY-раундам реестра,
но объяснение переносится всегда), справа `Switch` (`shrink-0`).

## 6. Поведение: загрузка / сохранение / ошибки

### 6.1 Загрузка

`useNotificationPreferences()` — `useQuery`, `queryKey: ['notification-preferences']`. Пока
`isLoading` — скелетон: на desktop 10 строк `<Skeleton className="h-5 w-full" />` в `<td colSpan={3}>`
(группировка не показывается, просто 10 одинаковых серых полос — группы появляются вместе с данными,
дешевле не рисовать фейковые заголовки групп); на мобайле — 10 карточек-заглушек той же формы, что
реальный ряд, но с `Skeleton` вместо текста/переключателя.

### 6.2 Сохранение — оптимистичное, без кнопки

`useUpdateNotificationPreference()` — `useMutation<void, Error, { type: NewNotificationType; email: boolean }>`:

```
onMutate({ type, email }):
  cancel queries ['notification-preferences']
  snapshot previous data
  setQueryData: заменить email для этого type в кэше (переключатель визуально прыгает сразу)
  return { previous }
onError(err, vars, context):
  setQueryData(context.previous)   // откат
  toast.error(`Не удалось сохранить настройку: ${msg}`)
onSuccess():
  toast.success('Сохранено')
onSettled():
  invalidate ['notification-preferences']  // подтвердить консистентность с сервером
```

Клик по `Switch` вызывает мутацию немедленно — без промежуточного «черновика». Пока мутация летит,
сам `Switch` можно оставить кликабельным (следующий клик просто ставит новую мутацию поверх) —
антипаттерна нет, потому что откат откатывает именно ту мутацию, которая упала, а `onSettled`
подтягивает актуальное состояние с сервера в конце. Если Coder предпочтёт блокировать повторный клик
на время in-flight мутации (`disabled={mutation.isPending}` вдобавок к `locked`) — тоже приемлемо,
не дизайн-требование.

### 6.3 Контракт API (проектируемый — сверить с 7a)

```
GET /notifications/preferences
→ Array<{ type: NewNotificationType; email: boolean; locked: boolean }>

PUT /notifications/preferences
body: { type: NewNotificationType; email: boolean }
→ 204 / обновлённая запись
```

Поле `inApp`/«в приложении» **не нужно в контракте** — колонка «В приложении» не читает данные,
это статическая подпись «Всегда» на каждой строке (см. допущение оркестратора: канал показывается,
но никогда не переключается). Если 7a всё же присылает такое поле — UI его игнорирует, это не
ошибка.

`locked` определяет: `Switch` рендерится с `checked={true}` (или `email === true` — оба должны
совпадать для locked-строк, но `checked` в любом случае форсируется в `true` на клиенте, даже если
бэкенд по ошибке прислал `false`, — недоступное состояние не должно визуально противоречить тексту
объяснения «отключить нельзя»), `disabled={true}`, `aria-disabled="true"`, клик не вызывает мутацию
(обработчик `onCheckedChange` не назначается или no-op).

## 8. Адаптив (320/375 · 768 · 1024/1280 · 1440/1920)

**Переключение верстки, а не CSS-реформат одной разметки.** По прецеденту `foundation.md` §10
(«плотная таблица → card-стек ИЛИ h-scroll») выбран **card-стек**, не horizontal-scroll: таблица
уведомлений — не денежная таблица с 6 колонками, где скролл был бы приемлем, а 3-колоночная с
длинным текстовым содержимым (объяснение locked-строк) — обрезание/скролл текста хуже, чем смена
формы. Технически — два независимых блока разметки под условием ширины:

```tsx
<div className="hidden md:block"> … <table> … </table> … </div>
<div className="md:hidden"> … per-row карточки … </div>
```

Это НЕ два дублирующих компонента с расползающейся логикой — оба читают один и тот же
сгруппированный массив (§2), различается только JSX-обёртка строки. Оба ветвления держат ОДИН
источник разметки строки на уровне вычисления (сгруппированные данные + текст), различие — только
в контейнере (`<tr>` vs `<div>`).

| Класс         | Ширины    | Поведение                                                                                                                                                                                                                                                                                                                                                              |
| ------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Мобильный** | 320 / 375 | Card-стек (§5.2). `Switch` — итоговый хит-эриа ≥44×44px (сам визуальный трек Radix уже компактный ~36×20 — обернуть в `inline-flex items-center justify-center` с `min-w-11 min-h-11`, паттерн, аналогичный `[&>button]:max-[639px]:min-h-11` из `project-status-filter.md` §5). Нет горизонтального скролла — весь текст переносится (`break-words`, без `truncate`). |
| **Планшет**   | 768       | Переключение на таблицу (`md:` breakpoint) — 768px уже комфортно вмещает 3 колонки при текущей type-scale (заголовки ≤24 символов, объяснение — самое длинное — переносится на 2-3 строки внутри своей ячейки, ячейка не фиксированной высоты).                                                                                                                        |
| **Ноутбук**   | 1024/1280 | Таблица, полная раскладка, без изменений относительно 768 кроме доступной ширины.                                                                                                                                                                                                                                                                                      |
| **Большой**   | 1440/1920 | Контент внутри `max-w-6xl` (общий кап `UserProfileShell.tsx`, уже применяется ко всем вкладкам) — таблица не растягивается на всю сверхширину, колонка «Тип уведомления» не превращается в нечитаемо длинную строку.                                                                                                                                                   |

**Тач-таргет ≥44×44 — единственный жёсткий number этой спеки помимо WCAG-минимума** (§9) — Radix
`Switch` по умолчанию рендерит `<button role="switch">` небольшого размера; обёртка должна расширять
именно **кликабельную область**, не визуальный трек (иначе трек визуально «раздувается» и не похож
на переключатель нигде в остальном UI — а мы этот компонент вводим впервые, задаём его вид один раз
для всего приложения).

## 9. A11y (WCAG 2.2 AA)

Проверено через skill `accessibility`.

- **`role="switch"` + `aria-checked`.** Radix `Switch` даёт это нативно (`data-state` +
  `aria-checked` синхронизированы) — не эмулировать вручную.
- **Лейбл связан с типом.** Каждый `Switch` — `aria-labelledby={id названия типа}` ИЛИ
  `aria-label={NOTIFICATION_TITLES[type] + ' — письмо'}` (второе проще и не требует генерации `id`
  на каждую строку; выбираю **`aria-label`** явно как решение этой спеки — конкатенация с «письмо»
  снимает неоднозначность «переключатель чего» при последовательном Tab по всем десяти строкам,
  где скринридер иначе объявил бы голый «переключатель» десять раз подряд без контекста).
- **`locked` → `aria-disabled="true"` + `aria-describedby`.** `aria-disabled`, не нативный HTML
  `disabled` — разница важна: нативный `disabled` убирает элемент из последовательности табуляции
  (пользователь скринридера вообще не узнает, что такая настройка существует и почему недоступна);
  `aria-disabled` держит элемент в Tab-порядке, но помечает недоступным — SC 4.1.2 требует, чтобы
  состояние было программно определяемо, а не чтобы элемент исчез. `aria-describedby` — на `id`
  параграфа объяснения В ЭТОЙ ЖЕ строке (per-row, не общий на группу — см. решение в §10 «Допущения»).
  Radix `Switch` поддерживает `disabled` prop, который по умолчанию мапится в нативный `disabled` —
  **явно передать `aria-disabled` отдельно** и НЕ полагаться на дефолтный маппинг, либо использовать
  `disabled={false}` + ручной `aria-disabled`/`onCheckedChange={undefined}` для visual-disabled без
  выпадения из Tab-порядка. Конкретный API вызова — на усмотрение Coder, требование зафиксировано.
- **Фокус.** `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2` — та же
  формула, что везде в этой кодовой базе (§3).
- **Порядок табуляции по строкам.** Естественный порядок DOM (группа → строка → `Switch`) уже даёт
  правильный порядок без `tabIndex`-трюков — группы и строки идут визуально сверху вниз, Tab идёт
  так же.
- **Target-size.** ≥44×44 на мобайле (см. §8) — крупнее WCAG-минимума 24×24 (SC 2.5.8), выбрано по
  `foundation.md` §9 «на мобайле целимся ≥44px».
- **Контраст.** `text-muted-foreground` на `bg-card`/`bg-background` — уже проверенная пара во всём
  приложении (не новая комбинация, замер не требуется).
- **Цвет не единственный носитель.** `locked`-состояние несёт три независимых сигнала: (1) текст
  объяснения — не просто визуально приглушённый переключатель; (2) `aria-disabled` — программно
  определяемо; (3) переключатель зафиксирован в положении «вкл» (не в неопределённом «сером»
  состоянии) — сам факт «включён и не трогается» уже сообщает «обязательно», без опоры на один цвет.

## 10. Допущения (A1, записаны, не эскалируются)

- **Объяснение locked — повторяется per-row, не выносится один раз на группу.** Задание описывает
  мобильную раскладку буквально как «название, под ним объяснение» — то есть построчно. Три
  повтора одного предложения (все три locked-типа делят один текст) стоят немного при трёх строках
  и делают `aria-describedby` самодостаточным на уровне строки — не нужно тянуть ссылку на id
  соседнего DOM-узла группы, что было бы более хрупко, если Coder решит виртуализировать строки
  или менять порядок группировки. Если владелец предпочтёт один общий блок под заголовком группы —
  правка тривиальна (убрать per-row абзац, добавить один под `<h3>Требуют ответа</h3>`,
  `aria-describedby` у всех трёх свитчей — на этот один id).
- **Порядок групп/типов — как в §2**, включая партиционирование `INFORMING_NOTIFICATION_TYPES` по
  предикату имени, а не по индексу массива (обоснование там же).
- **Заголовок вкладки внутри `CardContent`** («Уведомления» + подзаголовок, §5.1) — опционален:
  `AnimatedTabs` уже показывает «Уведомления» как подпись самой вкладки прямо над контентом, второй
  заголовок был бы избыточен по строгому чтению `foundation.md` («не пересказывать»); подзаголовок
  же несёт новую информацию («в приложении всегда») и оставлен. Coder может убрать заголовок
  «Уведомления» из `CardContent`, если сочтёт его дублирующим — не блокирует приёмку.
- **`Switch` — новый примитив вводится этой задачей**, а не берётся из внешнего готового места —
  подтверждено грепом каталога и `package.json` (§0.3). Стилизация — по токенам §3, без нового
  визуального языка.
- **Неизвестный тип не даёт переключать `Письмо`** (§7) — раз семантика неизвестна клиенту, ошибка
  в сторону «нельзя настроить» безопаснее ошибки «настроил не то, что думал».
- **RBAC-состав ролей, которым вообще открыта вкладка** (кроме исключения группы «Для
  администратора» — это отдельное, уже покрытое условие) — по умолчанию все self-роли, кроме тех,
  для кого backend не включит `'notifications'` в `permissions.tabs`. Спека не ограничивает список
  ролей сама — см. §12 (открытый пункт для security-reviewer/backend, не дизайн-решение).
