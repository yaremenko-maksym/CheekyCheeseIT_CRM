## ⚠️ 0. КРИТИЧНО — экспорт на украинском, реальная CRM на русском

Экспорт `vacancies-admin.dc.html` (и вложенные `VacancyCard.dc.html`/`CandidateCard.dc.html`)
сгенерирован **на украинском языке** (включая фейковый `Sidebar.dc.html`, который заявляет

Golden rule #7 (`ui-ux-designer.md`) и `.claude/rules/common/russian-language.md` — жёсткое
`ВСЕГДА RUSSIAN UI`, без исключений для баджей/тултипов/aria-label.

**Обязательно:** ВСЯ копия из макета переводится на русский при реализации. Полная таблица
перевода — §3.5 (статусы/бейджи) и §4 (все экранные строки, по месту). Домен-бейджи (`AI`/`EdTech`/

Seniority (`Senior`/`Lead`) — тоже латиница, но это ОТДЕЛЬНОЕ решение с собственным обоснованием
(см. §3.6) — не путать с переводом ролей CRM (`RoleSelect`: `SENIOR` → «Синьор»).

## 1. Направление (frontend-design-direction, кратко)

- **Purpose:** ADMIN/HR создают и публикуют вакансии, просматривают отклики кандидатов с публичной
  страницы карьеры, меняют статус вакансии/отклика, скачивают резюме, удаляют лишнее.
- **Audience:** HR/ADMIN — 1-5 раз в неделю, сканирует список вакансий и очередь новых откликов,
  быстро принимает решение (просмотрено/отклонено), не тратит время на лишние клики.
- **Tone:** `dense / quiet / scannable` — та же SaaS-operations эстетика, что и весь остальной CRM
  (карточки, а не таблица; статус — цветной dot + бейдж, не текст-в-строке).
  Домен-бейджи и dot-индикаторы — единственная «декоративная» деталь, всё остальное — рабочий стиль.
- **Memorable detail:** карточка кандидата с кольцом-подсветкой (`ring`) для непросмотренных
  откликов + inline-переключатель статуса (`SegmentedToggle`) прямо на карточке — HR не открывает
  отдельный диалог, чтобы отметить «просмотрено»/«отклонено».
- **Constraints:** Tailwind v4, shadcn/ui (`apps/web/app/components/ui/`), русский UI, WCAG 2.2 AA,
  responsive 320/768/1024/1440 (`.claude/rules/common/responsive-design.md`), zero новых npm-пакетов
  (весь визуал строится существующими примитивами и `lucide-react`, который уже в зависимостях).

### 3.2. Составные UI-паттерны — переиспользуем существующие примитивы вместо кастомных "табов"/"чипов"

Макет рисует три разных вида «переключателей» как чистые `<span>` с ручными стилями (не реальные
компоненты). В `apps/web` для этого уже есть **два** готовых примитива — используем их вместо
изобретения третьего:

| Где в макете                                                                                                                                  | Реальный компонент                                                                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| «Деталі / Відгуки» (переключение вкладок на странице вакансии)                                                                                | `AnimatedTabs` (`@/components/ui/animated-tabs`) — 2 таба, `value: 'details' \| 'applications'`, `label: 'Детали'` / `` `Отклики${count ? ` · ${count}` : ''}` ``                                                          |
| «Усі / Опубліковані / Чернетки / Закриті» (фильтр списка вакансий) и «Усі / Нові / Переглянуті / Відхилені» (фильтр откликов внутри вакансии) | `SegmentedToggle` (`@/components/ui/segmented-toggle`) `variant="tabs"` `role="tablist"` — page-level facet-фильтр, 4 и 4 опции соответственно, `label` включает счётчик текстом: `` `Все ${total}` ``, `` `Новые ${n}` `` |
| «Новий / Переглянуто / Відхилено» (быстрая смена статуса отклика прямо на карточке кандидата)                                                 | `SegmentedToggle` (`@/components/ui/segmented-toggle`) `variant="pill"` `size="sm"` — 3 опции, `value` = `application.status`                                                                                              |

**Известное отклонение от макета (см. также §8):** активный сегмент в макете для «Деталі/Відгуки» и
для фильтр-чипов — нейтральный `var(--card)` (не золотой). У `AnimatedTabs`/`SegmentedToggle`
активный сегмент **золотой** (`bg-primary` / `bg-primary/25`) — это уже устоявшийся паттерн всего
CRM (сайдбар, финансовые табы и т.д.). Переиспользуем как есть — золотой активный сегмент, не
заводим третий нейтральный вариант ради одного экрана.

**Расширение `SegmentedToggle` (рекомендуется, ~10 строк):** в макете сегмент «Відхилено» в
активном состоянии — красный (`color-mix(destructive 22%)`), а не золотой (см. `CandidateCard.dc.html`
`actRej` в `renderVals()`). Текущий `SegmentedToggle` красит активный сегмент одним `activePillStyles`
на все опции сразу — нет способа выделить один сегмент другим цветом. Рекомендация: добавить
опциональное поле `SegmentedToggleOption.activeVariant?: 'default' | 'destructive'` (влияет только на
цвет активного pill для ЭТОЙ опции — `bg-destructive/20 border-destructive/40` вместо
`activePillStyles`), использовать `activeVariant: 'destructive'` на опции «Отклонено». Если кодер
предпочитает не трогать общий компонент — fallback: все 3 опции с одинаковым золотым активным
сегментом (небольшая потеря визуального сигнала «отклонён = тревога», не блокирует AC).

### 3.3. Новое — расширение `badge.tsx` НЕ требуется (используем `className`-override)

Существующий паттерн (`document-card.tsx:170`: `<Badge variant="secondary" className="bg-red-500/15
text-red-600">PDF</Badge>`) — переопределение цвета через `className` поверх базового варианта,
БЕЗ добавления нового `variant` в `badgeVariants` cva. Следуем этому же паттерну для статуса вакансии
«Закрито» (единственный статус без готового варианта — см. §3.5 полную таблицу). Если появится ещё
2-3 места переиспользования того же красного "closed/rejected" паттерна — тогда стоит вынести в
`variant: 'status-rejected'` в `badge.tsx` (симметрично уже существующим `status-active`/
`status-closed`), но не сейчас (YAGNI, 1 использование).

### 3.4. Domain-tag цвета (dot-индикатор перед доменным бейджем)

Экспорт красит dot фиксированными oklch-hue (НЕ токенами темы — 3 разных hue нужны для
различения). **Сверка с сестринской спекой `docs/design/landing-redesign.md` §3.3** — та же задача
уже решена для публичной страницы `/careers` (лендинг): `--tag-ai` / `--tag-edtech` /
`--tag-ecommerce`. Используем **те же oklch-значения** для визуальной консистентности бренда между
публичной страницей карьеры и админкой (разные приложения — `apps/web` и `apps/landing` — токены
физически не шарятся между Vite-бандлами, но значения должны совпадать 1:1):

| Домен       | oklch                                                                                                   | CSS-переменная (добавить в `apps/web/app/styles/globals.css`, `:root`+`.dark`, аналогично landing-spec) |
| ----------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `AI`        | `oklch(84% .12 200)` (голубой)                                                                          | `--tag-ai`                                                                                              |
| `EDTECH`    | `oklch(82% .13 145)` (зелёный)                                                                          | `--tag-edtech`                                                                                          |
| `ECOMMERCE` | `oklch(80% .12 320)` (розово-фиолетовый)                                                                | `--tag-ecommerce`                                                                                       |
| `OTHER`     | нет отдельного hue — нейтральный, используем `var(--muted-foreground)` (без цветного dot, только серый) |

Если к моменту реализации `apps/landing` уже получил эти токены (спека `landing-redesign.md` мержится
независимо) — просто скопировать значения; порядок мержа не важен, значения фиксированы в обеих
спеках одинаково. Использовать ТОЛЬКО в доменном бейдже вакансии, нигде больше в CRM (не пересекается
с RBAC-палитрой ролей — другая семантика).

### 3.6. Seniority (`Senior`/`Lead`) — решение оставить латиницу (осознанное отклонение от «всё по-русски»)

`vacancySenioritySchema` (`SENIOR`/`LEAD`) — это **публичный job-title** кандидата на странице
карьеры (`apps/landing`, лендинг уже держит эти термины по-английски, см. `landing-redesign.md`), а
не внутренняя роль CRM. В отличие от `RoleSelect` (`SENIOR` → «Синьор» — внутренняя роль сотрудника
в системе), здесь `Senior`/`Lead` — общепринятые в рунете/укрнете IT-рекрутинге англицизмы для
названия позиции (как «Middle QA Engineer» в самом макете). Рекомендация: **отображать как есть**
(`Senior`, `Lead`), не переводить в «Синьор»/«Лід». Employment type (`FULL_TIME`/`PART_TIME`/
`CONTRACT`) — обычные русские слова, переводятся полностью (см. §4.2).

## 4. Layout по экранам и брейкпоинтам

### 4.1. Экран 1 — `/vacancies` (список)

**Шапка:** `h2` «Вакансии» + бейдж-счётчик «N всего» (`Badge variant="secondary"`) + подзаголовок
«Создавайте и публикуйте позиции, управляйте откликами кандидатов.» + кнопка `Button` (иконка `Plus`)
«Создать вакансию» справа (на ≤1024 — иконка + короткий текст «Создать», см. макет 1024/768px).

**Фильтр:** `SegmentedToggle variant="tabs"` — «Все N» / «Опубликованные N» / «Черновики N» /
«Закрытые N» (client-side фильтр по уже загруженному списку — 8-50 вакансий не требуют server-side
пагинации/фильтрации, YAGNI, см. §7 «50+»).

**Сетка карточек:** `grid grid-cols-1 lg:grid-cols-2 gap-[18px]` — 1440/1024 = 2 колонки (макет
показывает 2 колонки на 1440 в дефолте, 1 колонку в примере 1024 — фактическое решение: **2 колонки
с `lg:` (≥1024) достаточно места под карточку `~490px`**, ниже — 1 колонка). 768/320 = `grid-cols-1`.

**Карточка вакансии (`VacancyCard`):** заголовок + статус-бейдж (правый край, `flex-shrink-0`) →
ряд тегов (домен-dot-бейдж + seniority `Badge variant="secondary"` + employment
`Badge variant="secondary"`) → строка (иконка `MapPin` + локация · моноширинный `/careers/{slug}`)
→ `Separator` → нижний ряд: слева «N откликов» (иконка `Users`) + `N новых` бейдж (только если
`newCount > 0` и статус ≠ DRAFT), справа — action-кнопки по статусу (§4.1.1).

#### 4.1.1. Action-кнопки по статусу вакансии (source of truth — backend, НЕ буквально макет)

| Статус    | Кнопки (`size="sm"`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## 6. Скачивание резюме (presigned)

Endpoint `GET /api/vacancies/:vacancyId/applications/:appId/resume-url` → `{ url, expiresAt }`,
TTL 600с (10 мин, `RESUME_PRESIGN_TTL_SEC` в `applications.service.ts`). Паттерн 1:1 с
`useDocumentDownloadUrl` (`apps/web/app/hooks/use-documents.ts:96-111`):

```ts
// apps/web/app/hooks/use-vacancies.ts (новый файл)
export function useApplicationResumeUrl(
  vacancyId: string,
  appId: string | undefined,
  options?: { enabled?: boolean },
) {
  return useQuery<VacancyApplicationResumeUrl, Error>({
    queryKey: ['vacancies', vacancyId, 'applications', appId, 'resume-url'],
    queryFn: async () =>
      (await api.get(`/vacancies/${vacancyId}/applications/${appId}/resume-url`)).data,
    enabled: Boolean(appId) && (options?.enabled ?? true),
    retry: 1,
  })
}
```

Кнопка «Скачать резюме» → `await refetch()` → `window.open(result.data.url, '_blank',
'noopener,noreferrer')` (НЕ кешировать статично — presigned URL истекает через 10 мин, staleTime
короткий или 0, в отличие от `useDocumentDownloadUrl`, у которого `DOCUMENT_URL_STALE_MS` подобран
под документы с более долгим TTL — свериться с реальным TTL документов, не копировать staleTime
бездумно).

## 7. Confirm-диалоги (`AlertDialog`)

### 7.1. Удаление вакансии

Триггер — только когда кнопка не `disabled` (§4.1.1). Текст:
«Удалить вакансию?» / «Вакансия «{title}» будет удалена навсегда вместе с {N} откликами и
загруженными файлами резюме. Это действие необратимо.» — **на практике `N` всегда `0`** (кнопка
disabled при `applicationsCount > 0`), но текст держим общим (defensive — на случай гонки, если
отклик пришёл между открытием страницы и кликом «Удалить», backend всё равно вернёт 409, диалог не
должен утверждать точную цифру заведомо неверно; вариант — просто убрать упоминание количества
откликов из текста, раз оно всегда 0: «Вакансия «{title}» будет удалена навсегда. Это действие
необратимо.» — **рекомендуется этот упрощённый вариант**, короче и не может соврать).

### 7.2. Удаление отклика

Текст: «Удалить отклик?» / «Отклик кандидата {fullName} будет удалён. Загруженный файл резюме также
будет удалён с сервера. Это действие необратимо.» — **макет упоминает конкретное имя файла
(`dmytro_cv.pdf`) — в реальной схеме `vacancy_applications` НЕТ поля с оригинальным именем файла**
(`resumeS3Key`/`resumeSizeBytes` только, `resume-url` эндпоинт сам генерирует download-имя из
`fullName` на лету, см. `applications.service.ts:290-295` `sanitizeDownloadFilename(row.fullName)`)
— **не показывать имя файла в диалоге**, его просто нет как данных на фронте.

Оба диалога — `variant="destructive"` на `AlertDialogAction`, `AlertDialogCancel` — «Отмена».
409/ошибка мутации → `toast.error(error.response?.data?.message ?? 'Не удалось удалить')` (backend
уже возвращает готовый русский текст в `ConflictException`, просто прокинуть).

## 9. A11y (WCAG 2.2 AA критичные пути)

- **Target size (SC 2.5.8):** все интерактивные элементы ≥ 24×24px; на мобильных карточках (320) —
  явные `h-11 w-11` (44px) кнопки, как уже в макете (кебаб/иконка-only).
- **Focus order (SC 2.4.11):** Sheet при открытии переводит фокус на первое поле («Название
  вакансии»); `AlertDialog` (Radix) — автоматический focus-trap + фокус на `AlertDialogCancel` по
  умолчанию (Radix-конвенция, ничего доп. делать не надо); `Escape` закрывает и Sheet, и AlertDialog
  «из коробки» (Radix `Dialog`/`AlertDialog` primitives).
- **Контраст (SC 1.4.3):** статус-бейджи (`secondary`/`status-active`/красный `className`-override) —
  уже верифицированные токены темы (использовались в других местах CRM), не изобретать новые
  цветовые пары. Domain-dot цвета (§3.4) — decorative-only (сопровождаются текстовым label рядом,
  не несут смысловой нагрузки сами по себе — не обязаны проходить 4.5:1 как основной текст, но
  желательно ≥3:1 на фоне карточки, oklch-значения из landing-спеки уже подобраны под тёмный фон).
- **Icon-only buttons:** ВСЕ (удалить/редактировать/кебаб/восстановить-иконка) — обязательный
  `aria-label` (см. конкретные тексты по месту в §4/§5). Кебаб-меню на мобильном —
  `aria-label="Ещё действия"`.
- **`SegmentedToggle`/`AnimatedTabs`:** уже a11y-корректны из коробки (`role="radiogroup"`/`radio`
  или `role="tablist"`/`tab`, keyboard-доступны, см. исходники компонентов) — ничего доп. делать не
  нужно, только передать осмысленный `ariaLabel` контейнера («Фильтр вакансий по статусу», «Статус
  отклика кандидата {fullName}» и т.п.).
- **`<details>`/`<summary>`** («Сопроводительное письмо») — нативно доступно с клавиатуры и
  скринридерами без доп. работы.
