# Phase 8 — «Счёт компании» (USDT ERC-20) — BA-бриф / feature spec

**Status:** Draft for implementation (b0-deliverable планировочного цикла 2026-06-17).
**Prerequisite:** b0b Legal pre-check (см. §8) — ОБЯЗАТЕЛЕН до старта реализации (реальные USDT + дивиденды).
**Roadmap:** ADR `docs/architecture/2026-06-17-planning-audit-roadmap.md` Part 3(b), safety-gates Part 5.
**Заменяет:** отменённые смарт-контракты (Solidity PaymentSplitter / mainnet).

---

## 1. Суть

Единый **счёт компании** (кошелёк USDT ERC-20). SENIOR'ы и DROP'ы перечисляют на него деньги и
присылают **ссылку на транзакцию**; система верифицирует tx через Etherscan и зачисляет приход на
баланс счёта. ADMIN'ы тратят с этого счёта на зарплаты/расходы и выводят **дивиденды**.
Доли ADMIN'ов 50/50 сохраняются; появляется **общий счёт компании** как пул для расходов.

## 2. Решения владельца (2026-06-17) — зафиксированы

| #   | Вопрос                | Решение                                                                                                                                              |
| --- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Подтверждение прихода | **Полностью авто.** tx confirmed (≥ порог блоков) на адрес компании → сразу credit. Без ручного ACCOUNTANT-шага.                                     |
| 2   | Адрес кошелька        | **Один общий, в настройках.** ADMIN редактирует в настройках финансов; смена адреса — с подтверждением (security).                                   |
| 3   | Расчёт дивидендов     | **Свободный вывод, учёт постфактум.** ADMIN выводит произвольную сумму; система фиксирует движение + доли постфактум, без гейта «доступно к выводу». |

## 3. Flow прихода (авто)

1. SENIOR/DROP отправляет USDT на адрес компании (вне системы, в своём кошельке).
2. В CRM: форма «Подтвердить перевод» — вставляет **ссылку на транзакцию** (или tx-hash).
3. Бэк извлекает tx-hash, дёргает `etherscan.service.ts`:
   - tx найдена, получатель == адрес компании, токен == USDT ERC-20, **confirmed** (≥ порог блоков) →
     **авто-credit** на баланс счёта компании в размере фактической on-chain суммы tx.
   - tx **pending** (найдена, но < порога блоков) → UI **прогресс-бар резолва блоков**
     (текущие confirmations / порог), запись в статусе «в обработке», периодический re-poll.
   - tx не найдена / получатель не тот / не USDT → ошибка с понятным сообщением, credit НЕ происходит.
4. **Idempotency:** один tx-hash засчитывается РОВНО один раз (UNIQUE + проверка перед записью) —
   повторная отправка той же ссылки не дублирует приход.

## 4. Flow расходов / дивидендов

- **Расходы (общий счёт):** ADMIN тратит со счёта компании на зарплаты (существующий SALARY-flow) и
  прочие расходы. Списание уменьшает баланс счёта.
- **Дивиденды:** ADMIN инициирует вывод произвольной суммы как дивиденды; система фиксирует движение,
  уменьшает баланс, ведёт учёт долей 50/50 постфактум. Без авто-резерва/гейта (решение #3).

## 5. Модель данных (эскиз — финализируется в b1)

- `company_account` — баланс (или вычисляемый из ledger), адрес кошелька (настройка), валюта.
- Inbound deposits — `txHash` (UNIQUE), отправитель (SENIOR/DROP), сумма, статус
  (`PENDING_CONFIRMATION | CONFIRMED | FAILED`), confirmations, проверено-через-Etherscan timestamp.
- Outbound — withdrawals/dividends/expenses (тип, инициатор ADMIN, сумма, привязка к долям).
- **Ревизия legacy:** что делать с `payout_requests` / `pending_obligations` /
  `seniorSharePercent` / `dropSharePercent` / USDT-кошельками в `project_finance_settings` — определить
  в b1 (переиспользовать / мигрировать / депрекейтить). НЕ ломать существующую финмодель вслепую.

## 6. RBAC (separation-of-duties)

- **Приём прихода (submit tx):** SENIOR, DROP (свои переводы). Авто-credit — системный.
- **Вывод дивидендов / расходы со счёта:** только **ADMIN**. ACCOUNTANT видит/контролирует, но **не выводит**
  (ср. security MED #222 SALARY self-pay — не давать инициатору вывода быть бесконтрольным).
- **Адрес кошелька (настройка):** менять — только ADMIN, со step-up подтверждением.
- Все новые эндпоинты (submit-tx, withdraw, settings) → **реальный backend guard-тест 403** (FM-5 gate d1).

## 7. Acceptance criteria (черновик — детализируется в task-файлах)

1. Авто-credit срабатывает ТОЛЬКО на confirmed tx на адрес компании; pending → прогресс-бар, не баланс.
2. Idempotency: повторная отправка того же tx-hash не дублирует приход (integration-тест).
3. Дивиденды/расходы: только ADMIN (backend 403 для не-ADMIN — integration-тест).
4. Смена адреса кошелька: только ADMIN + подтверждение; audit-запись.
5. Etherscan недоступен/таймаут → graceful (прогресс-бар не зависает; статус «повторить»).
6. Дизайн прогресс-бара резолва блоков + страницы счёта — Mode A (ui-ux-designer) до верстки.
7. Сохранение 50/50 долей ADMIN в учёте; общий счёт корректно уменьшается на расходы/дивиденды.

## 8. Prerequisite — Legal pre-check (b0b, ОБЯЗАТЕЛЕН до реализации)

Компания-кастодиан USDT (приём от контракторов) + ADMIN-дивиденды → UA crypto/VASP/AML + налоговая
квалификация дивидендов. Skills: `ua-crypto-compliance` + `ua-tax-compliance`. Закон 2074-IX не введён,
ДПС-заборона крипто на ЄП. Money-movement = **human + legal** (правило). Реализация money-flow стартует
только после Legal-вердикта.

## 9. Open-вопросы для b1 (уточнить при проектировании)

- Порог подтверждений (дефолт-кандидат: 12 блоков ETH) — подтвердить.
- Сеть: USDT ERC-20 = Ethereum mainnet (читаем чужие переводы; контракт НЕ деплоим). Etherscan API mainnet.
- Баланс: хранимый агрегат или вычисляемый из ledger (предпочт. ledger — аудируемость).
- Что показывать SENIOR/DROP про их прошлые переводы (история + статусы).

## 10. Out of scope

- Любой on-chain smart contract / автономный split (отменено).
- Автоматическая отправка USDT из системы (вывод — ручное действие ADMIN вне сети; система фиксирует факт).
- Mainnet-деплой / аудит / multisig (не применимо — нет своего контракта).
