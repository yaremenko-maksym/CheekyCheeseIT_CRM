# Рефактор UX джуна — дизайн (2026-06-10)

> Статус: DRAFT на ревью владельца. Источник — brainstorming-сессия 2026-06-10.
> Следующий шаг после approve — implementation plan (writing-plans).

## 1. Контекст и цель

Текущий UX джуна разрознен и местами пуст: дашборд показывает только «—», финансы скудны и без контекста, документы путают категориями (disabled «Архив», неверный subtitle), навигация по чужим профилям ведёт в 403, в тулбарах виден ADMIN-шум.

**Цель — проекто-центричный реврейм.** Джун работает вокруг своего проекта и легенды-персоны «синьора»; не видит реальных синьоров/дропов и их данных; легенда становится живым per-project документом, который джун ведёт.

## 2. Принципы (сквозные правила)

1. **Проекто-центричность.** Дом джуна — «Мой проект» + «Легенда». Всё крутится вокруг проекта и персоны.
2. **Взаимная невидимость джун↔синьор/дроп.** Джун видит только персону легенды (через проект), никогда — реального синьора/дропа, их контакты или user-профиль. Синьор/дроп не видят джунов и не видят легенды (в т.ч. свою собственную).
3. **Всегда «синьор»; дропа для джуна не существует.** Что бы ни стояло за персоной на бэке (senior- или drop-юзер), джун видит и пишет «синьор». Слово «дроп» в интерфейсе и данных, доступных джуну, отсутствует.
4. **Финансовая граница.** Джун видит ТОЛЬКО свои приходы зарплаты. Ставка проекта (`rate`/`currency`), выплаты/распределения по проекту, доход синьора — скрыты.
5. **Легенда — живой документ.** Per-project персона, которую ведут ADMIN / HR / джун; джун дописывает новую информацию «на будущее».

## 3. Модель идентичности и легенды

**Легенда — сущность проекта, не подраздел профиля синьора.**

- Запись на пару `(projectId, userId)` — полная независимая персона. У одного синьора на проектах A и B — разные персоны (ФИО/ДР/адрес/хобби могут отличаться под каждого клиента).
- Концептуально легенда «переезжает» из профиля синьора в карточку проекта: «досье проекта — кто мы для этого клиента».
- Джун достаёт легенду через проект (`/api/projects/:projectId/legend`), никогда через `/api/users/:seniorId`.

**Содержимое легенды (три блока):**

1. **Персона «синьора»** (кто мы для клиента): ФИО · Дата рождения · Адрес · Хобби/интересы. Без фото — аватар по инициалам ФИО (реальное фото синьора джуну не показывается).
2. **Что клиент знает о нас** (cover story): презентуемая роль · заявленный стек · бэкграунд/история.
3. **Журнал** (append-only): лента записей `дата · автор · текст` — «что узнали / что клиент знает / договорённости». Механизм «появилась новая инфа → внёс на будущее».

**Редактирование:** ADMIN · HR (своей команды) · JUNIOR (активный member проекта). Синьор/дроп (субъект персоны) — не видит и не правит.

## 4. Целевой UX

**Навигация — 5 разделов** (Легенда вынесена отдельно из-за центральности):

`Мой проект · Легенда · Финансы · Документы · Профиль`

Убираем у джуна: отдельные «Команда» и «Проекты» (сворачиваются в «Мой проект»), просмотр чужих user-профилей, любой ADMIN-шум (фильтр «синьор» и т.п.).

### 🏠 Мой проект (хаб; заменяет пустой дашборд)

- **Карточка проекта:** лого · компания · домен · старт · статус. **Без ставки.**
- **Синьор проекта (персона):** аватар-инициалы · ФИО (из легенды) · презентуемая роль · → «Открыть легенду». Помечен как «синьор», никогда «дроп». Без реального фото/контактов.
- **Контракт:** статус (подписан / нужно подписать → CTA).
- **Моя зарплата (снимок):** последняя выплата (сумма/месяц/статус) → «Все мои выплаты». Только своё.
- **Ваш HR:** имя · контакт — через HR джун задаёт рабочие вопросы (синьора он не видит).
- **Быстрые ссылки:** Легенда · Документы · Финансы.
- Если активных проектов >1 — переключатель проектов вверху.

### 🎭 Легенда (персона-документ; джун ведёт)

Три блока из §3. Всегда «синьор». Редактирование персоны + cover + добавление записей в журнал (ADMIN/HR/джун).

### 💰 Финансы

Только свои SALARY-приходы с контекстом: проект · период · статус · сумма (+ расшифровать, что такое TX hash и статусы). Ни ставки, ни распределений, ни чужих финансов.

### 📄 Документы

Только релевантные джуну: своё резюме, сканы, свой контракт, инвойсы зарплат. Убрать disabled «Архив», поправить subtitle, не показывать недоступные категории как «сломанные».

### 👤 Профиль

Свои данные, реквизиты, свой контракт/онбординг. Без просмотра чужих профилей.

## 5. Данные и схема

```
-- было:
legends(id, userId UNIQUE, fullName, dateOfBirth, address, hobbies, notes, ts)

-- станет:
legends(
  id, projectId FK→projects(id) ON DELETE CASCADE,
  userId FK→users(id) ON DELETE CASCADE,
  fullName, dateOfBirth, address, hobbies,        -- персона
  presentedRole, presentedStack, backstory,        -- cover (что знает клиент)
  ts
)
UNIQUE(projectId, userId)   -- снять прежний UNIQUE(userId)

legend_entries(            -- журнал (append-only)
  id, legendId FK→legends(id) ON DELETE CASCADE,
  authorId FK→users(id), text, createdAt
)
```

**Миграция per-senior → per-project:** для каждой текущей `legends(userId=X)` скопировать запись в каждый активный проект, где `seniorId=X` ИЛИ `dropId=X`. Старое `notes` → первая запись журнала. Осиротевшие легенды (синьор без активных проектов) — **удаляются**.

## 6. RBAC

| Кто                         | Легенда проекта (view+edit) | Журнал         |
| --------------------------- | --------------------------- | -------------- |
| ADMIN                       | все                         | +              |
| HR (своей команды)          | да                          | +              |
| JUNIOR (активен на проекте) | да                          | + (дописывает) |
| Синьор/дроп (субъект)       | ❌                          | ❌             |
| Прочие                      | ❌                          | ❌             |

**Финансовая маскировка джуна:** проектные DTO не отдают `rate`/`currency`/распределения роли JUNIOR; `/api/finance/*` и transactions для джуна — только свои SALARY (уже частично, добить).

**Невидимость персон:** джун-facing проектные DTO заменяют реального синьора/дропа на персону легенды (ФИО из легенды, никаких реальных контактов/displayName/аватара), метка всегда «синьор».

**Побочный backend-фикс (по тому же принципу):** `getViewPermissions` — закрыть просмотр синьором других синьоров/дропов (сейчас `isSeniorViewingOwnProjectMember` пускает не-JUNIOR target). Не часть визуала джуна, но того же класса «не видят друг друга».

**Эндпоинты:** `GET/PUT /api/projects/:projectId/legend`, `POST /api/projects/:projectId/legend/entries`. Депрекейт `/api/users/:id/legend`.

## 7. Фазы внедрения

1. **Бэкенд (данные + RBAC + эндпоинты).** Миграция схемы + перенос данных; RBAC (легенда per-project; финмаскировка; персона-замена; синьор↔синьор невидимость); новые эндпоинты. Backend-тесты (403/маскировка) — обязательны (дисциплина RBAC-аудита, не mocked-E2E).
2. **UX ядро.** «Легенда» (персона + cover + журнал, джун редактирует) + «Мой проект» (хаб) + упрощение навигации до 5 разделов.
3. **UX чистка.** Финансы (своя зарплата + контекст), Документы (категории/архив/subtitle), Профиль (свой), убрать ADMIN-шум.

## 8. Решения (бывшие открытые вопросы)

1. **Поля cover** — `presentedRole` / `presentedStack` / `backstory`, как есть (достаточно).
2. **Осиротевшие легенды** при миграции — **удаляются**.
3. **Фото-персоны** — **не нужно** (аватар по инициалам ФИО).
4. **Несколько активных проектов** — основной кейс 1 проект (≈95%), поддержать до 2 (переключатель в «Мой проект»).
5. **Эскалация джуна** — **через HR** (контакт HR виден джуну в «Мой проект»).

## 9. Не входит в scope (явно)

- Активные фичи work-hub (задачи, чат, метрики) — отклонены (YAGNI) на этой итерации.
- Изменения UX синьора/дропа/HR/ADMIN, кроме backend-невидимости синьор↔синьор.
