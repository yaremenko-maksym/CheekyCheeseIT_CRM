### AC2. Из чего складывается доля уходящего партнёра

Доля партнёра — не одно число, а три разных, и ни одно не является строкой в БД.

**(а) HOLDING — сколько денег компании партнёр держит на руках.**
`getSummary.adminBalances` (`transactions.service.ts:5322-5352`):
`received − sent`, где
`received` = PAID-строки с `receiver_id = admin` и типом ∈ {`PAYOUT_ADMIN` (легаси, живого писателя нет),
`ADMIN_INCOME` с `funding_source ≠ 'COMPANY_ACCOUNT'`, `ADMIN_TRANSFER`, `PAYOUT_CONFIRMED`};
`sent` = **все** PAID-строки с `sender_id = admin`, любого типа.
Фильтра по `archivedAt` тут нет — намеренно (`:5306`, «departure ≠ automatic zero-out»).
Положительный HOLDING значит, что партнёр **держит** деньги компании, а не что компания ему должна.

**(б) DEBT — выравнивание холдингов между партнёрами 50/50.**
`DEBT = (HOLDING_A − HOLDING_B) / 2`; платит тот, у кого HOLDING больше.
**Этой формулы в коде нет вообще** — ни в API, ни в схеме, ни в DTO (`grep -i debt` по финансам даёт
только `debtToCompany` дропа). Она существует только в таблице владельца
(память `project_accounting_migration`: HOLDING Максим 78 238,34 / Костя 93 205,82 → DEBT 7 483,74).
**Именно это число и есть «расчёт с уходящим партнёром»**, и система его не знает.

**(в) Доля в счёте компании — неделимый пул.**
`computeCompanyAccountBalanceFromLedger` (`company-account-balance.ts:21-28`) — 8 членов, один скаляр.
Колонки «доля админа» в `users` нет (есть только `senior_share_percent` / `drop_share_percent`).
50/50 — договорённость, а не данные. Спека счёта прямо фиксирует режим: **«Свободный вывод, учёт
постфактум»** — админ выводит произвольную сумму дивидендов, гейта «доступно к выводу» нет
(`docs/business/2026-06-17-company-account-spec.md:23,42`). То есть система **намеренно** не моделирует
право партнёра на пул.

**Три читателя «баланса админа» дают три разных числа — и код это уже знает:**

| Читатель                                      | Формула                                                                            | Дивиденды      | Расхождение                                                                  |
| --------------------------------------------- | ---------------------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------- |
| `getSummary.adminBalances`                    | `PAYOUT_ADMIN + ADMIN_INCOME(≠пул) + ADMIN_TRANSFER + PAYOUT_CONFIRMED − ВСЕ sent` | **не считает** | по `receiver_id`                                                             |
| `BalanceService.getAdminBalance`              | `ADMIN_INCOME(≠пул) + DIVIDEND_TO_ADMIN − PAID EXPENSE`                            | считает        | по `recipient_id ?? receiver_id`                                             |
| `BalanceService.getTotalEarned` (ветка ADMIN) | `PAYOUT_ADMIN + DIVIDEND_TO_ADMIN + ADMIN_INCOME_CASH/CRYPTO`                      | считает        | `ADMIN_INCOME` **не** считает; два из четырёх типов никогда не эмитировались |

Комментарий на `transactions.service.ts:5175-5186` прямым текстом: «Reconciling the two MODELS into one
number is a separate, not-yet-scoped decision». Пока это решение не принято, **любая автоматика
расчёта выберет одно из трёх чисел молча**.

**Где расходится с сеньором и дропом:**

|                             | SENIOR                                               | DROP                                          | ADMIN (партнёр)                            |
| --------------------------- | ---------------------------------------------------- | --------------------------------------------- | ------------------------------------------ |
| Строка долга при начислении | `pending_obligations` + `SENIOR_PENDING_PAYOUT`      | `pending_obligations` + `DROP_PENDING_PAYOUT` | **нет** (`senior.role !== 'ADMIN'`)        |
| Величина                    | зафиксирована в строке (`amount`), доля заснапшочена | то же                                         | производная, три несовпадающих определения |
| Момент фиксации             | при заходе дохода                                    | при заходе дохода                             | никогда                                    |
| Путь погашения              | `settleByCompany`, `manualConfirmPayout`             | те же                                         | **нет**                                    |
| Что видит архивация         | список PENDING (по решению 2026-08-18)               | то же                                         | `{ noDependencies: true }`                 |
| Направление                 | всегда «компания должна»                             | всегда «компания должна»                      | **любое из двух**                          |

**Две вещи, которые в бэклоге не названы и меняют дизайн:**

1. **Расчёт двунаправленный.** Уходящий партнёр может быть должен компании (если его HOLDING выше) —
   в проде сегодня это ровно так для Кости. `pending_obligations` **не умеет** выражать «пользователь
   должен компании»: `creditor_user_id NOT NULL` (`schema.ts:1262`), а у компании нет строки в `users`;
   enum `debtor_type` (`:143-148`) описывает только должника, но не кредитора-компанию. То есть
   «просто завести обязательство, как у сеньора» покрывает лишь половину случаев.
2. **Половина расчёта уже открыта, и не с той стороны.** Гварды закрывают только приход
   архивному. Уход **от** архивного не закрыт намеренно (`:3805-3811`) — и `ACCOUNTANT` может
   провести `ADMIN_TRANSFER` с явным `senderId` чужого админа (`:3778`, BIZ-06 запрещает это только
   ADMIN-вызывающему). Ни `settleByCompany`, ни `paySalary` не проверяют `archivedAt` у
   `payerAdminId` (`pending-settlement.service.ts:396`, `transactions.service.ts:6406`).
   Практический вывод: **направление «партнёр платит» работает сегодня без единой правки**, а
   направление «партнёру платят» закрыто полностью. Дополнительный побочный эффект: оставшиеся
   партнёры могут списывать HOLDING ушедшего, назначая его плательщиком чужих зарплат и обязательств.

**Ещё один капкан рядом, тот же корень.** Каскадная архивация ветвится по `user.role`
(`users.service.ts:1078` — ветка `SENIOR`), а владение проектом живёт в `projects.senior_id`, который
роль не проверяет. В конфигурации «админ как сеньор» эти два ключа расходятся: архивация партнёра
не заденет его активные проекты вообще, и правило владельца от 2026-08-19 («сеньора нельзя убрать
поодиночке — команда и проекты разом») на него не распространится. На проде это не гипотетика —
активные проекты принадлежат админу.

## Decision (AC3) — предлагаемый способ

### Принцип — тот же, что в решении владельца от 2026-08-18

Решение по зарплатам разграничивает **не по состоянию человека, а по происхождению строки**:
созданное — заработано и остаётся выплачиваемым; новое создаётся только активным.

У партнёра строки нет. Значит механизм того же устройства — это **не новый способ платить
архивному**, а **момент, в который строка появляется**: строка расчёта создаётся **в транзакции
архивации**, то есть пока человек ещё активен. Дальше она ведёт себя ровно как IOU сеньора: остаётся,
остаётся погашаемой, показывается в модалке, закрывается существующим путём. После архивации новых
строк не создаётся — все пять гвардов остаются на месте.

### Вариант 1 (рекомендуемый) — «расчётная строка при архивации», деньги идут существующими каналами

**Что создаётся.** Одна строка в новой таблице `partner_settlements`:
`user_id`, `direction` (`COMPANY_OWES` | `PARTNER_OWES`), `amount`, `currency`,
`basis` (текст — на чём владелец остановился: HOLDING/DEBT/договорённость), снимки трёх чисел на момент
архивации (`holding_snapshot`, `counterpart_holding_snapshot`, `pool_snapshot` — как справка, не как
источник суммы), `created_by`, `created_at`, `settled_amount`, `closed_at`, `status`
(`OPEN` | `SETTLED` | `WRITTEN_OFF`).

**Почему отдельная таблица, а не `pending_obligations`.** Обязательства однонаправлены
(`creditor_user_id NOT NULL`, компания-кредитор невыразима), а расчёт двунаправлен. Плюс любая новая
строка в `pending_obligations` требует парной строки-транзакции (`source_transaction_id NOT NULL`), то
есть нового типа транзакции — см. вариант 3, почему это дорого.

**Сумму вводит владелец, система её не вычисляет.** Три числа расходятся, а действующее (DEBT) не
вычисляется вообще; выбрать одно молча — значит зашить бизнес-правило, которого нет. Модалка
показывает все три как справку и **требует ввести сумму и основание**. Это дискреция — но
**однократная, в момент ухода, при живом партнёре, зафиксированная неизменяемой строкой с автором**,
а не открытый навсегда канал (что и было предметом опасений #564).

**Кто и когда.** Тот же ADMIN, который выполняет архивацию, в той же транзакции: сумма и основание →
строка `partner_settlements` → `archived_at`. Атомарно (иначе возможно состояние «архивирован без
расчёта», которого ни одна ветка не предусматривает). Сумма = 0 → строка не создаётся (симметрия с
«нет PENDING → модалки нет»).

**Как погашается — без единого нового денежного пути:**

- `COMPANY_OWES`, доля из пула → **`DIVIDEND_TO_ADMIN`**. Это уже действующий и единственный канал
  партнёрской доли (`payout-no-admin-split.integration.spec.ts`: «Admin income is now a deliberate
  manual flow (DIVIDEND_TO_ADMIN)»). У него уже есть: член в формуле счёта, advisory-lock,
  гейт «не уводить счёт в минус», обязательный чек, идемпотентность.
- `COMPANY_OWES`, выравнивание холдингов → **`ADMIN_TRANSFER`** от оставшегося партнёра. Счёт компании
  не задействован (в 8-членной формуле члена `ADMIN_TRANSFER` нет — `company-account-balance.ts:348`),
  что арифметически верно: это перекладывание между холдингами.
- `PARTNER_OWES` → **`ADMIN_TRANSFER` с `senderId` ушедшего**, оформляет ACCOUNTANT. **Работает уже
  сегодня**, править нечего.

**Что меняется в гвардах — ровно два, и не удалением строки:**

```
// было
if (receiver.archivedAt) throw new BadRequestException(...)
// станет
if (receiver.archivedAt && !hasOpenSettlementBudget(receiver.id, amount)) throw ...
```

Только в `createDividend` (`company-account.service.ts:717`) и `createAdminTransfer`
(`transactions.service.ts:3827`). Остальные три (`createAdminIncome`, `declareUsdtProjectIncome`,
`confirmPayout`) **не трогаются**: там причина другая — «для проводки нужна активная сторона», а не
«нельзя платить» (это различие уже зафиксировано в коде на `:3679-3685`).

Строка расчёта — не флаг, а **бюджет**: сумма разрешённых выплат не может превысить `amount`; при
исчерпании `status → SETTLED` и гвард снова закрывается сам. Нет строки → поведение байт-в-байт
сегодняшнее.

**Что делает архивация (модалка).** ADMIN-ветка `getArchiveImpact` (`users.service.ts:1473`) сегодня
возвращает `{ noDependencies: true }`, а диалог печатает **«Связанных сущностей нет»**
(`ArchiveConfirmDialog.tsx:248`) — для уходящего партнёра это неправда. Ветка расширяется до того же
набора секций, что и модалка из `task-archive-pending-modal` (AC8): (1) непогашенные PENDING,
(2) активные проекты/команды под каскад — **включая проекты, где партнёр является `senior_id`**,
(3) новая секция расчёта: три справочных числа + обязательные поля «сумма» и «основание».
Отмена не архивирует и не создаёт строку.

**Стык с каскадом (решение владельца 2026-08-19).** Ветвление по роли надо заменить/дополнить
ветвлением по факту владения: «есть активные `projects.senior_id = user.id`» → каскад команды и
проектов, одной операцией, независимо от того, `SENIOR` роль или `ADMIN`. Джуниоры и HR на этих
проектах, по решению от 2026-08-19, **не трогаются** — их `archivedAt` не меняется, начисления идут
как обычно. Для партнёра это тем более важно: его проекты — самые населённые.

**Уверенность.** HIGH — что механизм воспроизводит устройство решения 2026-08-18 и не открывает
дискреционного канала. HIGH — что `DIVIDEND_TO_ADMIN` / `ADMIN_TRANSFER` покрывают обе стороны без
нового типа. **LOW — по способу получения суммы**: это бизнес-решение (см. открытые вопросы), и
пока владелец не выберет, автоматизировать нельзя.

## Consequences (AC4) — что ломается в каждом варианте

### Вариант 1 (рекомендуемый) — чем он **хуже** остальных

- **Требует ввода от человека.** Сумму нельзя посчитать кнопкой; если владелец ошибётся в поле,
  система пропустит ошибку — арифметической защиты нет (у сеньора она есть: доля заснапшочена).
  Смягчение: три справочных числа рядом + `basis` обязателен + строка неизменяема (правка = отмена
  и новая строка со ссылкой на прежнюю).
- **Новая таблица** — миграция + прод-DDL (только через `deploy.yml`, SSH к VPS нет) + новый экран
  «незакрытые расчёты», иначе строка станет невидимым долгом. Вариант 2 не требует ни того, ни другого.
- **Ослабляет два гварда, которые сейчас абсолютны.** Абсолютный гвард нельзя обойти ошибкой в
  условии; условный — можно. `hasOpenSettlementBudget` становится денежным гейтом со всеми
  вытекающими (TOCTOU: проверка и списание должны быть в одной транзакции под тем же
  advisory-lock'ом, что и остальные списания со счёта, — иначе два параллельных вывода дважды съедят
  один бюджет).
- **Атомарность архивации усложняется**: архивация + расчётная строка + каскад проектов = одна
  транзакция. Сейчас архивация — уже транзакция, но каскад партнёра туда ещё не входит.
- **Не решает расхождение трёх читателей** — только обходит его, показывая все три. Расхождение
  останется и всплывёт в первом же споре «а почему тут одна цифра, а там другая».

### Вариант 2 — «архивация запрещена, пока расчёт не сведён к нулю»

Партнёр рассчитывается, **оставаясь активным** (обычные `DIVIDEND_TO_ADMIN` / `ADMIN_TRANSFER`, без
единой правки), и только потом архивируется. Нужен один гейт в `archive`.

- **Что ломается:** доступ отзывается **последним**, а не первым. Уходящий партнёр всё это время
  видит все финансы, все проекты, всю команду и может проводить операции — включая перевод денег
  себе. Это ровно тот сценарий, для которого деактивация и понадобилась, а конфликтный уход может
  длиться месяцами.
- «Ноль» недостижим механически: HOLDING — производная от **всех** отправленных строк, она движется
  от любой операции партнёра. Гейт «архивируй при нуле» превратится в гонку с самим партнёром.
- Не отвечает на вопрос «какое из трёх чисел равно нулю».
- **Хорош чем:** нулевая новая машинерия, ни один гвард не ослаблен, реализуется за один PR. Это
  разумный **временный** ответ, если деактивация нужна раньше, чем владелец выберет модель суммы.

### Вариант 3 — новый тип транзакции `PARTNER_SETTLEMENT_PENDING` + `pending_obligations`

Максимальная симметрия с сеньором: строка-IOU + обязательство + погашение через `settleByCompany`.

- **Что ломается:** `settleByCompany` разбирает исходный тип на два случая, и «всё остальное»
  попадает в ветку сеньора (`pending-settlement.service.ts:305,309`) — партнёрская выплата станет
  `SENIOR_INCOME` и **дёрнет `autoCreateForSeniorPayout`**, то есть сгенерирует подписываемый
  инвойс сеньора на партнёрскую выплату. Нужна третья ветка.
- Формула счёта компании — **9-й член**, иначе выплата из пула не спишется с пула (фантомные деньги,
  тот же класс дефекта, что уже чинили в `computeCompanyAccountBalanceFromLedger`).
- Новый тип надо провести через **каждый** агрегат вручную. Прецедент в этом же файле:
  `getAdminBalance` годами суммировал типы, которых никто не эмитирует, и молча возвращал 0
  (`balance.service.ts:123-140`) — компилятор ловит только `Record<TransactionType, string>` в UI,
  но не формулы.
- Двунаправленность всё равно не выражается: `creditor_user_id NOT NULL`.
- **Хорош чем:** одна модель обязательств на всех, один экран «долги компании», ноль новых таблиц.

### Вариант 4 (антивариант) — просто снять гвард

Это то, что произойдёт **по умолчанию**, если решение не принять: автор деактивации упрётся в
«Получатель архивирован — дивиденды не выплачиваются», удалит строку (или добавит `|| isPartnerPayout`)
и получит: дискреционную выплату любому архивному админу, любой суммы, в любой момент, без основания
и без следа — притом что архивный админ в систему не заходит и подтвердить получение не может.
Ровно тот исход, ради предотвращения которого писались комментарии в обеих точках гварда.

## AC5. Проверка на проде — read-only SQL для владельца, дальше СТОП

К `crm_db` не подключался. Ниже — запросы **только на чтение**; прогоняет владелец, реализация
начинается после его ответа.

```sql
-- (0) Куда подключились. Выполнить ПЕРВЫМ и убедиться глазами.
SELECT current_database(), version();

-- (1) Архивных ADMIN быть не должно (ожидание: 0 строк).
SELECT id, display_name, archived_at FROM users WHERE role = 'ADMIN' AND archived_at IS NOT NULL;

-- (2) Валюты в строках, участвующих в HOLDING. Если тут есть что-то кроме USD/USDT,
--     запрос (3) НЕ равен формуле приложения (оно конвертирует по НБУ) — читать с поправкой.
SELECT t.currency, count(*), sum(t.amount)
FROM non_deleted_transactions t
JOIN users u ON u.role = 'ADMIN' AND (u.id = t.receiver_id OR u.id = t.sender_id)
WHERE t.status = 'PAID'
GROUP BY t.currency ORDER BY 2 DESC;

-- (3) HOLDING каждого партнёра по формуле getSummary.adminBalances (#311).
WITH a AS (SELECT id, display_name FROM users WHERE role = 'ADMIN'),
recv AS (
  SELECT a.id, COALESCE(SUM(t.amount), 0) AS received
  FROM a LEFT JOIN non_deleted_transactions t
    ON t.receiver_id = a.id AND t.status = 'PAID'
   AND (t.type IN ('PAYOUT_ADMIN', 'ADMIN_TRANSFER', 'PAYOUT_CONFIRMED')
        OR (t.type = 'ADMIN_INCOME' AND t.funding_source IS DISTINCT FROM 'COMPANY_ACCOUNT'))
  GROUP BY a.id),
sent AS (
  SELECT a.id, COALESCE(SUM(t.amount), 0) AS sent
  FROM a LEFT JOIN non_deleted_transactions t
    ON t.sender_id = a.id AND t.status = 'PAID'
  GROUP BY a.id)
SELECT a.display_name, recv.received, sent.sent, (recv.received - sent.sent) AS holding
FROM a JOIN recv ON recv.id = a.id JOIN sent ON sent.id = a.id
ORDER BY holding DESC;

-- (4) DEBT = (H_больший - H_меньший)/2. Кто кому должен на сегодня.
--     Считать по результату (3) вручную: двух партнёров проще сверить глазами,
--     чем прятать в CTE, которое молча даст неверное число при трёх админах.

-- (5) Второе определение того же числа — насколько оно расходится с (3).
--     getAdminBalance: ADMIN_INCOME(≠пул) + DIVIDEND_TO_ADMIN − PAID EXPENSE(sender=admin)
SELECT u.display_name,
  COALESCE(SUM(t.amount) FILTER (WHERE t.type = 'ADMIN_INCOME'
        AND t.funding_source IS DISTINCT FROM 'COMPANY_ACCOUNT'
        AND COALESCE(t.recipient_id, t.receiver_id) = u.id), 0)
+ COALESCE(SUM(t.amount) FILTER (WHERE t.type = 'DIVIDEND_TO_ADMIN'
        AND COALESCE(t.recipient_id, t.receiver_id) = u.id), 0)
- COALESCE(SUM(t.amount) FILTER (WHERE t.type = 'EXPENSE' AND t.sender_id = u.id), 0)
  AS balance_service_number
FROM users u LEFT JOIN non_deleted_transactions t ON t.status = 'PAID'
WHERE u.role = 'ADMIN' GROUP BY u.id, u.display_name;

-- (6) Баланс счёта компании (8 членов) — величина, из которой берётся доля в пуле.
SELECT
   COALESCE(SUM(amount) FILTER (WHERE type = 'COMPANY_DEPOSIT'), 0)
 + COALESCE(SUM(amount) FILTER (WHERE type = 'PAYOUT'        AND funding_source = 'COMPANY_ACCOUNT'), 0)
 + COALESCE(SUM(amount) FILTER (WHERE type = 'ADMIN_INCOME'  AND funding_source = 'COMPANY_ACCOUNT'), 0)
 - COALESCE(SUM(amount) FILTER (WHERE type = 'DIVIDEND_TO_ADMIN'), 0)
 - COALESCE(SUM(amount) FILTER (WHERE type = 'SALARY'        AND funding_source = 'COMPANY_ACCOUNT'), 0)
 - COALESCE(SUM(amount) FILTER (WHERE type = 'EXPENSE'       AND funding_source = 'COMPANY_ACCOUNT'), 0)
 - COALESCE(SUM(amount) FILTER (WHERE type = 'SENIOR_INCOME' AND funding_source = 'COMPANY_ACCOUNT'), 0)
 - COALESCE(SUM(amount) FILTER (WHERE type = 'PAYOUT_DROP'   AND funding_source = 'COMPANY_ACCOUNT'), 0)
 AS company_account_usdt
FROM non_deleted_transactions WHERE status = 'PAID' AND currency = 'USDT';

-- (7) Сколько проектов повиснет: активные проекты, чей senior — ADMIN.
SELECT u.display_name AS admin_senior, count(*) AS active_projects
FROM projects p JOIN users u ON u.id = p.senior_id
WHERE p.archived_at IS NULL AND u.role = 'ADMIN'
GROUP BY u.display_name;

-- (8) Живые PENDING-обязательства и не архивирован ли уже кредитор.
SELECT po.status, po.debtor_type, u.role, u.display_name,
       u.archived_at IS NOT NULL AS creditor_archived,
       count(*), sum(po.amount::numeric)
FROM pending_obligations po JOIN users u ON u.id = po.creditor_user_id
WHERE po.status = 'PENDING'
GROUP BY 1, 2, 3, 4, 5 ORDER BY 7 DESC;

-- (9) Легаси PAYOUT_ADMIN в проде (живого писателя нет; строки могли остаться от импорта).
SELECT count(*), sum(amount) FROM non_deleted_transactions WHERE type = 'PAYOUT_ADMIN';
```

```bash
git rm docs/architecture/2026-08-19-departing-partner-settlement.md

# ожидаемое состояние: git status чист, файла в docs/architecture/ нет,
# поведение кода не менялось ни на одном шаге (проверка: git diff origin/main -- apps/ packages/ пуст)
```

условием — гвард возвращается в абсолютный) → модалка → таблица (`DROP TABLE partner_settlements`,
данных к тому моменту 0..N строк, каждая с автором и основанием).
