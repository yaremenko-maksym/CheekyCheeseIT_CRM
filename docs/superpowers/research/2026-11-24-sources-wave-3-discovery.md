# Sources wave 3 — Phase 1 discovery (robots and terms read)

**Date:** 2026-11-24. **Work order:** `.claude/tasks/task-sources-wave-3.md` (Phase 1). **Extends:**
[`2026-11-24-new-source-candidates.md`](2026-11-24-new-source-candidates.md), the first-pass survey whose verdicts
were provisional because no terms had been read. This file supersedes its verdicts.

**Shelf life:** robots files and terms change without notice. Every quote below was true on 2026-11-24. Before a
coder builds an adapter, the task file re-fetches the robots lines for the exact paths it will request. A row older
than 30 days at build time is re-read, not trusted.

## Method

- **NO_EVASION.** Plain `curl`, the default User-Agent, one request per document, no account, no key request, no
  proxy, no headless browser. A `403`, `429` or a bot challenge ended work on that host, and the row says so.
- **Robots are judged for `User-agent: *`.** The production fetcher sends its own honest User-Agent
  (`CheekyCheeseIT-CRM/1.0 (job sourcing; +https://cheekycheese.tech)`), which no robots file names, so the
  wildcard group is the one that applies to it.
- **Terms were read**, not guessed. Each terms cell quotes the clause on automated access or reuse, with a link to
  the page it came from, or says why the terms could not be read.
- **Quotes were checked mechanically.** Every quote was matched against the raw page saved for its own host.
  171 of 173 quotes match. The two that do not (Factorial and iCIMS terms) are marked `unverified:` in the
  table, and both rows are `no` for other reasons.
- **The origin was a developer machine, not production.** A site may answer a datacenter IP differently (a bot
  wall, a geo block). So every build row passes a probe from the production host before its PR is dispatched:
  one robots request and one feed request with the production User-Agent. A row that fails the probe drops out.
- **Three rows were not examined** (`not-examined`): the host refused or timed out from the local origin before
  anything could be read. They are retried from the production probe.

## Two verdict columns

The table has two verdict columns, and they mean different things:

- **evidence verdict** is what the evidence alone supports: `add`, `owner-decision` (a fork only the owner can
  settle: unclear terms, a free key, off-profile market) or `no`.
- **owner decision 2026-11-24** is what the wave builds. The owner answered in chat on 2026-11-24:
  1. Every `owner-decision` row is pre-approved ("add everything possible").
  2. Sites whose terms explicitly forbid automated collection are connected too (the owner accepts that risk).
     These rows read `add (terms ban accepted by owner)`.
  3. Hard limits stay: no login, no paid plan, no bot wall, captcha, `403` or `429`, no robots `Disallow` on a
     path we need. A row that fails any of these stays `no` whatever its terms say.

Exceptions to the pre-approval:

- **cvkeskus.ee is held.** Its terms (clause 2.10) set a contractual fine of 10,000 EUR for automated collection.
  A fine of that size needs its own owner answer.
- **remote.com/jobs is `no`.** The product shuts down on 2026-11-30.
- **Free-key sources wait for the owner's signup.** Agents never register accounts or request keys. The owner
  registers, puts the key in the production secrets, and the adapter reads it from config: Careerjet partners
  API, web3.career, NAV arbeidsplassen, itjobs.pt.

## Build plan (families)

Every new source is one new `job_source_type` enum label. All labels land first in one PR (W3-0), so the source
PRs do not collide on the enum migration. Source PRs then go by family, in waves of at most three coders, merged
one at a time. Only rows that pass the production probe are built.
