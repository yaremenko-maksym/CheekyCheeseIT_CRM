2026-05-22 [P1] [retro-session-after-archive-pr] #approval #communication Sequence intent ≠ approval. «Сначала вмерджим X, потом Y» — это план, а не команда мерджить X сейчас. При любой двусмысленности задавать одно clarifying Q: «мерджим X прямо сейчас?» — не предполагать. Конкретно: преждевременный merge PR #35 произошёл потому что я (PM) трактовал план как approval.
2026-05-22 [P1] [retro-session-after-archive-pr] #visual #communication Короткое visual feedback (скриншот + 3 слова «выровняй по вертикали») — НЕ делать первую правдоподобную интерпретацию. Задать одно clarifying Q: «выровнять cells между колонками или contents внутри row?». Конкретно: на round 9 я сделал 2-row структуру для «no junior», а проблема была в `min-h-19` на outer wrapper — двойная итерация на одной проблеме.
2026-05-22 [P2] [retro-session-after-archive-pr] #visual #communication Для нетривиальных visual багов (скриншот без аннотаций) — присылать пользователю свою интерпретацию ДО dispatch Coder: «Я понял что нужно X — правильно?». Лучше потерять 1 раунд диалога чем впустую запустить Coder на 12 мин.
2026-05-23 [P0] [dev-flow-rca] #worktree #hygiene ScheduleWakeup не выживает session boundary. Для cross-session ожидания (> 30 мин) — сохранять `next_action` в `pm-state.json`, при Mode 3 catch-up при missed wake-up. См. CLAUDE-pm.md секция «ScheduleWakeup limitations» + sub-task `task-harness-schedule-wakeup-persistence.md`.
2026-05-23 [P0] [task-pm-cross-session-waits] #wakeup #scheduler Полноценный обход D1 — `mcp__scheduled-tasks__*` (external scheduler выживает session boundary). PM запускает `scripts/pm/pm-schedule.sh` для подготовки параметров (fireAt, taskId, materialized prompt), потом вызывает MCP-tool. Каждый wake-up создаёт fresh PM-сессию с self-contained prompt из `scripts/pm/wakeup-prompts/<template>.md` — нет утечки контекста из source-сессии. Layer 1 (`ScheduleWakeup`) — для in-session коротких wait'ов; Layer 2 (`mcp__scheduled-tasks`) — для длинных/критичных. Не смешивать оба слоя на один wait — это создаёт дубли fire'ов.
2026-05-23 [P0] [dev-flow-rca] #silent-completion #recovery Coder может silently завершиться без push (watchdog cutoff). Если Coder не отвечает > 10 мин после dispatch — читать `docs/specs/tasks/<task>.progress.md` (sentinel), сравнивать `last_update` vs `last_push`. Если расхождение > 5 мин — `git -C <coder-worktree>` достать незакоммиченную работу.
