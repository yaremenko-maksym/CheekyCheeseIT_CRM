## 1. Порядок мержа (важно, историческая запись)

Этот infra-PR (`infra/drop-share-pending-parity-ddl-wiring`) должен был лечь в
`main` **ДО или ВМЕСТЕ с** PR #443 (`fix/drop-share-pending-parity`) — не после.
Причина: как только #443 попадёт в `main` без этой обвязки, деплой пойдёт по
путям, для которых сейчас применяется только фикс кода (`bookCompanyObligations`
и HIGH-1-гейт в `settleByCompany`), но не схема (`drop_cascade_origin` колонка) —
новый api-образ упадёт на первом же обращении к каскадному дроп-пути, потому что
колонки ещё нет. Каждый шаг ниже поэтому **guarded** (см. §6) — до мержа #443 он
notice-скипается (файла ещё нет в чекауте), деплой остаётся зелёным весь этот
промежуток, и никакого отдельного действия при мерже #443 не требовалось — guard'ы
переходят из «skip» в «работает» автоматически на следующем прогоне (тот же
паттерн, что у telemetry/CSP-reports, см. §6). Это уже произошло — PR #443 в
`main`, шаги активны.

**Раунд 4 review (важное дополнение к семантике).** Маркерная колонка
`drop_cascade_origin` — nullable, без дефолта; серверный гейт в
`settleByCompany` блокирует COMPANY_ACCOUNT-settle на ЛЮБОМ значении, кроме
явного `false` (то есть и `true`, и `NULL` — fail-CLOSED). Сам маркерный файл
(`2026-07-27_drop_cascade_origin_marker.sql`) поэтому уже несёт СВОЙ
собственный backfill — это не отдельный файл, это встроенный **STEP 3** внутри
того же .sql (STEP 1 — singleton state-таблица `drop_cascade_origin_marker_state`,
STEP 2 — схема/колонка, STEP 3 — сам `UPDATE`). Этот файл должен применяться
**дважды** за одну выкатку — см. §4.

**Раунд 6 review (self-referential граница, не календарная дата).** Предикат
STEP 3 — `WHERE drop_cascade_origin IS NULL AND type = 'DROP_PENDING_PAYOUT' AND
created_at < first_applied_at + INTERVAL '24 hours'`, где `first_applied_at` —
момент первого в жизни ЭТОЙ БД применения файла (записан один раз, в STEP 1,
`ON CONFLICT DO NOTHING`). Отсечка НЕ календарная и намеренно ловит строки,
созданные ПОСЛЕ добавления колонки — это не баг, это то, ради чего существует
второй проход (Step 3.5, см. §4): строка, созданная старым api-образом в
узком окне между двумя проходами маркера в рамках ОДНОЙ выкатки, физически
создаётся позже добавления колонки, и без этого свойства предиката второй
проход был бы логически бессмысленным.

## 2. Почему это ЗАДУМЫВАЛОСЬ как две выкатки (security-review MED-2) — и почему до второй не дошло

Второй раунд review PR #443 указал: порядок «маркер → перенос» энфорсится
машинно (перенос ссылается на колонку `drop_cascade_origin` — без маркера упадёт
и откатится), а порядок «подсчёт → перенос» машинно НЕ защищён — держится только
на дисциплине того, кто пишет шаги деплоя. Плюс исходная шапка backfill-файла
предписывала применять перенос ДО нового api-образа — это открывало окно, где
конвертированные записи уже существуют, а серверный запрет (`settleByCompany`
HIGH-1 гейт) и блокировка в UI — ещё нет (старый api-контейнер всё ещё
обслуживает трафик, пока новый образ подтягивается/стартует).

**Спроектированная схема — две выкатки:**

- **Выкатка N** (нормальный push/`workflow_dispatch`/weekly rebuild после мержа
  #443): применяются, в этом порядке — маркер, **первый проход** (Step 2k, со
  своим встроенным `UPDATE`) → **подсчёт** (Step 2l, read-only) → подъём
  контейнеров + все FATAL health/smoke-проверки (Step 3) → маркер, **второй
  проход** (Step 3.5, тот же файл повторно — см. §4). Новый api-образ несёт
  HIGH-1-гейт и UI-блокировку. Перенос (Step 4, тогда ещё существовавший) НЕ
  выполняется — гейт `APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL` по умолчанию
  OFF.
- **Владелец читает число** из job summary этой выкатки (§7) и решает.
- **Выкатка N+1** (отдельный, более поздний прогон, гейт явно включён
  владельцем) — задумывалась как момент, когда применяется сам перенос.

**Фактический итог (2026-08-01, run 30691783655).** Выкатка N состоялась на
проде — это был **первый прод-прогон precount после мержа #443**. Он напечатал:

```
drop-share-pending-parity PRE-COUNT (read-only, no writes yet): 0 Path-B rows
```

Ноль. На проде не оказалось ни одной записи, созданной обходным путём, который
PR #443 закрывает — переносить было нечего. Гейт `APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL`
ни разу не включался (оставался в дефолтном OFF всё это время), Выкатка N+1 не
понадобилась. Задача task-infra-drop-share-backfill-dewire (2026-08-01) сняла
Step 4 и гейт из `deploy.yml` целиком — см. §3/§5.

## 4. Маркер — второй проход (Step 3.5, security-review HIGH-1 round 4; permanent, round 5/6)

**Проблема, которую закрывает этот шаг.** Step 2k применяет маркерный файл
ДО подъёма новых контейнеров (Step 3) — пока идёт pull/restart/health-check,
СТАРЫЙ api-образ (предыдущей выкатки, ничего не знающий про эту колонку) всё
ещё обслуживает трафик и продолжает создавать `DROP_PENDING_PAYOUT` строки
(обычные декларации через `declareUsdtProjectIncome`) с `drop_cascade_origin =
NULL` — тот самый пробел, который Step 2k's `UPDATE` не мог поймать, потому что
эти строки появились МОМЕНТОМ позже. Оставленные так, они навсегда и ошибочно
блокируются от легитимного COMPANY_ACCOUNT-закрытия гейтом `<> false` — компания
реально держит эти деньги, но закрыть долг с её счёта нельзя, а UI при этом
преселектит «Счёт компании» и своим же текстом ошибки укажет заплатить с личного
счёта админа, что исказит реестр (тот самый вред, ради которого HIGH-1 писался).

**Round 6 — откат api-образа закрыт ТОЛЬКО частично, не полностью.** Тот же
пробел открывается заново при откате (rollback) api-образа назад до версии
без этой колонки (старый образ снова обслуживает трафик, ничего не зная о
колонке) — но если откат происходит БОЛЬШЕ чем через 24 часа после первого
применения маркера на этой БД (`first_applied_at`), он падает ВНЕ окна STEP 3
(`first_applied_at + INTERVAL '24 hours'`): строки, которые забронирует
откаченный образ, останутся `NULL` и потребуют ручного проставления (см.
`UPDATE transactions SET drop_cascade_origin = false WHERE ...` вручную по
конкретным id). Второй проход маркера закрывает race окна cutover'а ИМЕННО
ЭТОЙ выкатки, а не произвольно-поздний откат.

Строки, оставленные непойманными до следующей выкатки, — не мелочь: между
выкатками могут пройти дни (обычный ритм мержей, плюс еженедельный rebuild как
верхняя граница), и всё это время долг компании перед конкретным человеком
нельзя закрыть с её счёта.

**Фикс.** Тот же самый маркерный файл (`2026-07-27_drop_cascade_origin_marker.sql`)
применяется ЕЩЁ РАЗ — **Step 3.5** в `deploy.yml`, физически ПОСЛЕ Step 3
(`docker compose up -d` api/nginx) и после ВСЕХ FATAL health/smoke-check'ов
выше по скрипту. К этому моменту новый образ подтверждённо жив и отвечает
`/api/health`, старый — подтверждённо остановлен, новых непроставленных строк
от ЭТОГО cutover'а больше не появится. STEP 1 файла (singleton state-таблица) и
STEP 2 (схема) — оба no-op (состояние и колонка уже сошлись на Step 2k);
STEP 3 (`UPDATE ... WHERE ... IS NULL AND ... AND created_at < first_applied_at + INTERVAL '24 hours'`)
— идемпотентен, ловит только строки, появившиеся в окне между Step 2k и
Step 3.5 (и попадающие под ту же 24-часовую границу).

### 4.1 Почему это НЕ тот же гейт, что был у переноса — и почему снятие не нужно

Второй проход маркера **не** гейтился через
`APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL` (переменная и код, читавший её,
удалены — §3) и не требует отдельного включения владельцем — он выполняется
**безусловно** на каждой выкатке (тот же file-presence guard, что у Step 2k —
soft-skip до мержа #443), в отличие от бывшего переноса:

- **Перенос (бывший Step 4, снят §3)** — историческая мутация данных,
  требовавшая суждения владельца о риске/объёме (сколько строк, какая сумма) —
  поэтому явный opt-in, и после применения — обязательное снятие (пример
  процедуры, которую этот runbook описывал §5 до 2026-08-01), потому что это
  разовая мутация, небезопасная для повторного прогона на будущих данных. На
  проде он так и не применился (0 строк) — снят целиком.
- **Второй проход маркера (Step 3.5)** — механическое закрытие узкого,
  понятного race condition окна деплоя. Владельцу тут нечего решать —
  задержка через опциональный гейт просто оставила бы окно открытым по
  умолчанию на каждой обычной выкатке, что и есть сам баг.

**Снятие НЕ требуется (round 5 review — пересмотр решения round 4; граница
уточнена round 6).** В предыдущей ревизии этого runbook второй проход
считался одноразовым и подлежащим снятию — по аналогии с переносом. Это было
пересмотрено: `UPDATE` внутри самого маркерного файла (STEP 3) ограничен не
календарной датой, а **self-referential** границей —
`created_at < first_applied_at + INTERVAL '24 hours'`, где `first_applied_at`
записывается ОДИН РАЗ в STEP 1 (singleton state-таблица
`drop_cascade_origin_marker_state`, `ON CONFLICT DO NOTHING` — каждый
последующий запуск читает то же самое значение, никогда его не сдвигая). Эта
отсечка **намеренно** захватывает строки, созданные ПОСЛЕ добавления колонки
(иначе второй проход, ради которого она и существует, был бы логически
бессмысленным) — «до добавления колонки» здесь ни при чём. Это меняет
свойство файла:

- И первый (Step 2k), и второй (Step 3.5) проход **никогда не могут** тронуть
  строку, вставленную БУДУЩИМ, корректно проставляющим маркер кодом — потому
  что `first_applied_at` заморожен навсегда после первого применения на этой
  БД, и любая строка, созданная через дни/недели ПОСЛЕ него, физически не
  попадает под `< first_applied_at + 24h`, сколько бы раз файл ни применялся.
- Поэтому обычный риск «безусловно повторяющийся `UPDATE` молча патчит
  регрессию, которая забыла проставить колонку» — сюда неприменим: такая
  регрессия (если она возникнет через недели/месяцы после первого применения)
  создаст строку ВНЕ окна, файл её не заденет, и гейт `<> false` в
  `settleByCompany` честно заблокирует её, как и задумано (fail-CLOSED
  сохраняется для будущих регрессий — весь смысл round 4). Ровно тот же
  предикат — причина, по которой откат образа больше чем через 24ч после
  `first_applied_at` НЕ закрывается автоматически (см. Round 6 в §4 выше) —
  свойство симметрично для «регрессии кода» и «отката образа»: оба вне окна
  после первых суток остаются `NULL`/заблокированы намеренно, а не по ошибке.
- Оба прохода одного и того же файла становятся симметричны по безопасности:
  что первый, что второй — идемпотентные, детерминированные, ограниченные
  прошлым по времени. Ни один не нуждается в снятии, гейте или критерии
  готовности — оставить впаянными навсегда так же безопасно, как схемную
  часть файла (`ADD COLUMN IF NOT EXISTS`).

### 4.2 ВНИМАНИЕ: якорь — одна строка в служебной таблице — НЕ УДАЛЯТЬ

**Security-review PR #443 (MED-1, round 6).** Вся граница §4/§4.1 держится
ИСКЛЮЧИТЕЛЬНО на выживании одной строки: `first_applied_at` в
`drop_cascade_origin_marker_state`. Это служебная таблица, которой **нет** в
описании схемы (`schema.ts`/Drizzle её не знает — она не через ORM создана и
не через `db:push` управляется). Ничто не отличает «первый честный штамп» от
«состояние потеряли и переставили».

**Как якорь может молча потеряться** (любой из этих сценариев переоткрывает
окно):

- восстановление прод-БД из бэкапа, снятого ДО первого применения файла;
- синхронизация схемы в разработке (`drizzle-kit push` в dev не знает о
  таблицах вне схемы — по неосторожности её можно случайно не перенести или
  дропнуть при пересоздании dev-БД с нуля);
- ручной `TRUNCATE`/`DROP TABLE drop_cascade_origin_marker_state` при какой-
  либо уборке (например, по аналогии с прецедентом де-вайринга §5 — НЕ делать
  то же самое с этой таблицей).

**Последствие потери — тихое, не failure.** Следующее применение файла
перештампует `first_applied_at = now()`, и окно **молча откроется заново на
24 часа**: ВСЕ `NULL`-строки `DROP_PENDING_PAYOUT`, существующие в БД на этот
момент (включая исторические, давно прошедшие через нормальный fail-CLOSED
режим), получат `false`. `RAISE NOTICE 'backfilled=N'` на рутинной выкатке
никто не читает как тревогу — это просто ещё одна строка в
`$GITHUB_STEP_SUMMARY` (см. §7).

**Правило: таблица `drop_cascade_origin_marker_state` (и особенно её
единственная строка) НИКОГДА не удаляется и не пересоздаётся вручную.** Она
входит в контур обычного бэкапа БД наравне с `transactions` — восстановление
БД из бэкапа, снятого ПОСЛЕ первого применения файла, безопасно (переносит и
`first_applied_at`); восстановление из бэкапа, снятого ДО — небезопасно (см.
выше) и требует ручной проверки после restore (сверить `first_applied_at` в
таблице с реальной датой первого прод-деплоя #443/#447, прежде чем доверять
границе).

## 5. Де-вайринг переноса (Step 4) — ВЫПОЛНЕНО 2026-08-01

Из трёх файлов снятия после использования требовал **только перенос**. Маркер
(оба прохода — Step 2k и Step 3.5, см. §1/§4) и подсчёт (Step 2l) остаются
впаянными навсегда — гейта и процедуры снятия у них нет и не нужно.

Разовая мутация денежных статусов была НЕ идемпотентна навсегда: предикат отбора
(`type='PAYOUT_DROP' AND status='PAID' AND payout_request_id IS NOT NULL`)
был безопасен только потому, что PR #443 УДАЛЯЕТ единственный код-путь,
который мог произвести такую строку, и `settleByCompany` всегда обнуляет
`payout_request_id` при закрытии — но ничто не гарантировало бы, что НИКАКОЙ
будущий код никогда больше не создаст PAID+PAYOUT_DROP+живой
`payout_request_id`, если бы шаг остался впаянным бессрочно. Прецедент того же
паттерна — PR #382 (auto-wire) → PR #383 (de-wire после одного успешного
прогона), settle-phantom-cleanup data-fix.

**Что фактически произошло (task-infra-drop-share-backfill-dewire, 2026-08-01):**

Первый прод-прогон precount после мержа #443 (run 30691783655) напечатал
`0 Path-B rows` — применять было нечего, а гейт `APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL`
ни разу не флипался в `true` (оставался в дефолтном OFF). Поэтому вместо
«применили → снять» цикл закрылся веткой «нечего было применять → снять сразу»:

1. Из `deploy.yml` удалён весь блок Step 4 (от баннера `# Step 4: drop-share
pending-parity BACKFILL...` до соответствующего `fi` перед
   `echo "==> Cleaning dangling images"`), включая проверку файла и
   apply/tee-блок.
2. Из `env:` того же ssh-action шага удалена строка
   `APPLY_DROP_SHARE_BACKFILL: ${{ vars.APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL == 'true' }}`
   (маркер/precount её не использовали).
3. Из `envs:` того же шага удалено `,APPLY_DROP_SHARE_BACKFILL`.
4. `2026-07-27_drop_share_pending_parity_backfill.sql` убран из
   `copy-compose`'s scp-списка (`FILES=...` в guard-шаге и комментарий в
   copy-шаге) — маркер+precount продолжают копироваться, они остаются
   активными.
5. `check-prod-ddl-wiring.py` — файл добавлен в `KNOWN_NOT_WIRED` с причиной
   «применение не требуется — предварительный подсчёт на проде дал 0 строк,
   run 30691783655; новые записи этого класса невозможны после выкатки #443»
   (тот же паттерн, что `2026-07-15_settle_phantom_cleanup_auto.sql` в том же
   файле).
6. Repository variable `APPLY_DROP_SHARE_PENDING_PARITY_BACKFILL` можно
   оставить как есть (неустановлена/`false`) — код, который её читал, удалён,
   значение больше ни на что не влияет.
7. Сам SQL-файл `2026-07-27_drop_share_pending_parity_backfill.sql` НЕ удалён
   из репозитория — остаётся историческим артефактом в
   `apps/api/drizzle/manual/` (зона Coder'а, не DevOps).
8. Backup-таблица `_drop_share_pending_parity_backup_20260727` на проде — её
   не существует (перенос не применялся, backup-таблицу создавать было не с
   чего) — в отличие от прецедента settle-phantom-cleanup, где backup остаётся
   после реального применения.

Маркер (оба прохода) и подсчёт снятия не требуют — см. §4.1 почему; подсчёт
остаётся постоянным как страховка: если он когда-нибудь напечатает не ноль,
это будет сигнал, что появился путь, которого мы не знаем (см. §3).

## 7. Куда смотреть за числом (job summary, не лог)

Каждый прогон `deploy` job'а добавляет секцию **«Drop-share pending-parity —
DDL output (money-affecting, PR #443)»** в GitHub Actions **Job Summary** (не
только в живой лог) — механика:

1. Главный SSH-шаг ("Pull, up, migrate, health-check via SSH") пишет
   RAISE NOTICE-вывод обоих проходов маркера + precount в
   `/opt/crm/.last-ddl-summary.txt` на VPS (`tee -a`, файл усекается в начале
   каждого прогона).
2. Отдельный маленький шаг "Fetch drop-share-pending-parity DDL summary via SSH"
   (`capture_stdout: true`, `if: always()`) читает этот файл через SSH и
   отдаёт его как `steps.dspp_ddl_summary.outputs.stdout`.
3. Шаг "Publish drop-share-pending-parity DDL summary to job summary"
   (`if: always()`) дописывает его в `$GITHUB_STEP_SUMMARY` кодовым блоком.

С 2026-08-01 (после де-вайринга §3/§5) этот вывод больше не может содержать
блок BACKFILL — только маркер (×2) и precount, всегда.

Смотреть: `gh run view <run-id>` → вкладка Summary в GitHub UI, или
`gh run view <run-id> --log | grep -A50 "Drop-share pending-parity"` для
CLI-варианта. Разделены на два отдельных маленьких шага (не `capture_stdout` на
всём гигантском деплой-шаге), чтобы не буферизовать/скрывать live-вывод
health-check retry-циклов главного шага — регрессия, не связанная с этой
задачей.
