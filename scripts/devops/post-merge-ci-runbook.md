# Post-merge CI — runbook

> **Скоуп:** task-infra-post-merge-ci (2026-07-27). Валидация фактического
> состояния `main` после мержа + оповещение о красном main.
> Workflows: `.github/workflows/ci.yml` (jobs `quality` / `integration` /
> `e2e` / `post_merge_alert`), `.github/workflows/auto-merge-on-label.yml`.
> Скрипт алерта: `scripts/devops/post-merge-alert.sh`.

---

## 1. Проблема, которую это закрывает

Проверки гонялись только на `pull_request` — против merge-коммита PR, а не
против того `main`, который получился после мержа. Если два PR по отдельности
зелёные, но конфликтуют **семантически** (текстовый конфликт поймал бы git),
поломка обнаруживалась только на следующем PR — а прод к тому моменту уже
задеплоен, потому что деплой стартует сразу после мержа.

### 1.1 Почему `push: branches: [main]` не помогал

Триггер `push: branches: [main]` в `ci.yml` **был с самого первого коммита**
репозитория — и всё равно последний прогон CI на main датировался
**2026-06-13**. Причина: каждый мерж — это сквош от `auto-merge-on-label.yml`
через `GITHUB_TOKEN`, а GitHub **не создаёт push-события** для пушей,
сделанных `GITHUB_TOKEN` (anti-recursion). То есть триггер был мёртвым:
он срабатывал только на ручной пуш/мерж владельцем через UI.

Ровно эта же гоча уже была решена для деплоя (см. шапку `deploy.yml`,
канал №2): `workflow_dispatch` — документированное исключение из
anti-recursion. Здесь применено то же лекарство.

**Вывод для будущих задач:** наличие `push:`-триггера в workflow НЕ означает,
что он отрабатывает. Проверять фактом: `gh run list --branch main --workflow=<wf>`.

## 2. Как это работает сейчас

| Событие                                  | Что срабатывает                                                      |
| ---------------------------------------- | -------------------------------------------------------------------- |
| Мерж через `merge-approved` (обычный)    | `auto-merge-on-label.yml` → сквош → dispatch `deploy.yml` + `ci.yml` |
| Ручной пуш / UI-мерж / revert владельцем | нативный `push`-триггер `ci.yml` и `deploy.yml`                      |
| Ручной прогон                            | `gh workflow run ci.yml --ref main`                                  |

**Merge-путь ровно один.** Job `auto_merge` внутри `ci.yml` (второй, спящий
путь) **удалён** 2026-07-27 по итогам ревью — он нёс `contents: write` +
`actions: write` в workflow с триггером `pull_request`, что для веток этого
репо давало вектор self-merge (ветка могла переписать условие с меткой в своей
merge-ref версии файла). Причина и чек-лист — в комментарии на месте удалённого
job'а в `ci.yml`.

**Оба диспатча гейтятся по результату сквоша явно** (`if: always() &&
steps.squash.outcome == 'success'`), а не по дефолтному `success()` предыдущих
шагов. Иначе они выстраивались в цепочку: упал диспатч деплоя → шаг диспатча CI
не выполнялся вообще, и post-merge валидации молча не было.

Двойного прогона не бывает: сквош от `GITHUB_TOKEN` не даёт push-события
(работает только dispatch), ручной пуш даёт push-событие (dispatch'а нет) —
та же схема доказательства, что в шапке `deploy.yml`.

### 2.1 Что именно гоняется post-merge

**Полный набор:** `quality` (typecheck / lint / unit) + `integration`
(Postgres) + все 7 E2E-шардов. Урезания нет — обоснование в §3.

`Lighthouse` (`lighthouse.yml`) в post-merge **не входит** осознанно: это
PR-гейт, скоупленный на `apps/landing/**`, с порогами, чувствительными к шуму
раннера (`numberOfRuns=5` + медиана как раз ради флаки-устойчивости). Красный
Lighthouse на main породил бы alert-fatigue на сигнале, который не про
корректность. Перф прода наблюдается отдельно.

### 2.2 Scope-резолюция (важный нюанс)

`dorny/paths-filter` теперь вызывается **только на `pull_request`**. На
push/dispatch scope принудительно `code=true` — шаг `Resolve run scope` в
каждом из трёх job'ов.

Причина: paths-filter строит диапазон из base..head PR'а. Вне PR он
сравнивает дефолтную ветку саму с собой, и неверная догадка тут даёт «нет
изменений» → весь post-merge прогон коротит в **молчаливый зелёный**. Это
ровно тот исход, ради предотвращения которого гейт и делался, поэтому scope
вне PR задаётся явно, а не выводится.

Цена: docs-only мерж тоже гоняет полный набор (~22 job-минуты). Минуты на
публичном репо бесплатны — размен принят сознательно.

Резолвнутый scope виден в Job Summary прогона (`### CI scope`) — если
post-merge прогон когда-нибудь всё же скоротит работу, это будет видно, а не
замаскировано зелёной галкой.

## 3. Стоимость (почему не урезали)

Замер по реальному **post-merge** прогону (`gh run view 30262209085` — мерж
PR #441): 12 job'ов, самый длинный ~5 мин, суммарно **~33 job-минуты**,
wall-clock **~5 мин** (всё параллельно).

> Первая редакция этого файла ссылалась на прогон `30244912815` и приводила
> «~22 job-мин / ~10 мин wall-clock». Аудит показал, что это был
> `pull_request`-прогон (не post-merge), и что оба числа неверны: реально там
> 27.4 job-мин и 4 мин 46 сек. То есть job-минуты были занижены, а wall-clock
> завышен вдвое — post-merge прогон **быстрее**, чем обещал рунбук. Цифры выше
> перемерены по правильному прогону.

Репозиторий **публичный** → GitHub Actions minutes на стандартных раннерах
**бесплатны**. Денежная стоимость post-merge прогона = 0, поэтому урезание
до «только typecheck/lint/unit» или прогон по расписанию раз в N часов —
это ухудшение сигнала без выигрыша в деньгах.

Что реально стоит: конкурентность раннеров (post-merge прогон делит пул с
CI активных PR) и alert-fatigue. Отсюда — прогон **на мерж**, а не по
расписанию (по расписанию хуже: поломка живёт в проде дольше, а привязка к
конкретному мержу теряется).

**Если картина поменяется** (репо станет приватным / упрёмся в лимиты
конкурентности): урезать в таком порядке — (1) выкинуть из post-merge шарды
`landing` и `misc`, (2) оставить только `quality` + `integration` + шард
`drop-finance` (money-path), (3) перевести E2E на расписание раз в 6 часов,
оставив `quality`/`integration` на каждый мерж.

## 4. Алерт о красном main

Job `post_merge_alert` (`ci.yml`) агрегирует три ноги и вызывает
`scripts/devops/post-merge-alert.sh`.

**Канал:** приватный репо `yaremenko-maksym/cheekycheese-telemetry` через
`TELEMETRY_ISSUES_PAT` (тот же секрет, что у telemetry-digest) — это канал,
который реально просматривается. Если PAT отсутствует **или не работает** —
**фолбэк** на issue в публичном `CheekyCheeseIT_CRM` через `GITHUB_TOKEN` +
`::warning`.

Канал выбирается по **работоспособности** токена, а не по его наличию: шаг
`Resolve alert channel` делает пробный `gh issue list --limit 1` по приватному
репо. Так и должно быть — протухший fine-grained PAT это НЕПУСТАЯ строка, и
проверка «переменная не пуста» считала бы его валидным, после чего `gh issue
list` в скрипте отдавал бы 401, `set -euo pipefail` ронял бы скрипт до создания
issue, и алерт исчезал бы в тишину (найдено ревью PR #441 — первая редакция
обещала фолбэк, но не делала его). Сам скрипт дополнительно не полагается на
`set -e`: сбой запроса списка issue = `exit 3` + `::error`, а не тихий обрыв.

**Граница канала (не размывать):** тело алерта — только метаданные прогона
(SHA, subject, имена упавших job'ов, ссылка на run). Никаких выдержек из логов,
stacktrace'ов и env: при недоступном PAT это уходит в **публичный** репо.
`COMMIT_SUBJECT` — недоверенная строка (заголовок смерженного PR), поэтому в
issue попадает в бэктиках и обрезанной до 120 символов: канал читает ассистент,
а markdown/prompt-инъекция в AI-читаемый канал — реальный вектор.

**Состояния** (ровно один открытый issue по метке `ci-main-broken`):

| Результат прогона       | Открытый issue есть | Действие                    |
| ----------------------- | ------------------- | --------------------------- |
| `failure`               | нет                 | создать issue               |
| `failure`               | есть                | комментарий (без дубля)     |
| `success`               | есть                | закрыть с комментарием      |
| `success`               | нет                 | ничего                      |
| `cancelled` / `skipped` | —                   | ничего + `::warning` (ниже) |

Job дополнительно падает при `failure`, чтобы красный main был виден и в
Actions UI, а не только issue'й.

**Про `inconclusive`.** Сюда попадает не только штатная отмена по
`cancel-in-progress` (следующий мерж обгонит прогон и провалидирует
надмножество — это нормально), но и инфра-сбои: job не стартовал, раннер умер,
docker-pull таймаут на `Initialize containers` (был прецедент —
[[project_stale_main_and_ci_infra_failures]]). Во втором случае main остался
**не провалидированным**, а issue не откроется. Поэтому шаг печатает
`::warning` с командой перезапуска — молчание тут выглядело бы как «всё
хорошо».

### 4.1 Локальная проверка скрипта (dry-run)

Скрипт вынесен из workflow именно ради этого — логику алерта можно прогнать
без пушей:

```bash
DRY_RUN=1 ALERT_REPO=owner/repo GH_TOKEN=dummy \
  COMMIT_SHA=deadbeef RUN_URL=https://example/run/1 \
  RESULT=failure FAILED_LEGS="quality, e2e" \
  ./scripts/devops/post-merge-alert.sh
```

`DRY_RUN_OPEN_ISSUE=42` дополнительно симулирует «алерт уже открыт» — так
проверяются ветки дедупа и авто-закрытия.

### 4.2 Отношение к `e2e-broken`

`notify_e2e` (метка `e2e-broken`, протокол «команда на паузе») **не тронут** —
это агент-facing блокер, на который завязаны `contracts.md` и `coder.md`.
`post_merge_alert` — про весь прогон и про уведомление ассистента. При падении
E2E на main откроются оба: разные аудитории.

⚠️ **`e2e-watchdog.yml` ОТКЛЮЧЁН** (`if: false`) этим же циклом. Он слушал
`workflow_run: [CI], branches:[main]` и спал ~1.5 месяца именно потому, что CI
на main не завершался. Включив post-merge прогон, мы его **разбудили** — а
внутри у него checkout с `ADMIN_PAT`, `git commit && git push` напрямую в
`main` и dispatch удалённого `autotest.yml`. Авто-коммит в main это настоящее
push-событие (PAT, не GITHUB_TOKEN) → триггерит деплой красного состояния →
снова красный CI → снова авто-коммит: самоподдерживающийся цикл, который
`concurrency` не гасит. Не выстрелило только потому, что путь к шаблону в нём
битый. Условия возрождения — в шапке `e2e-watchdog.yml`.

> **Урок общего вида:** включение мёртвого триггера — это не только «теперь
> запускается то, что хотели». Проверяй, кто ещё подписан на это событие
> (`workflow_run`, `push`, `check_suite`) и что он делает с правами.

Одно исправлено: условие `notify_e2e` раньше выполнялось при **любом**
`workflow_dispatch` — то есть диспатч на фиче-ветке мог открыть «команда на
паузе». Теперь требуется `github.ref == 'refs/heads/main'`.

## 5. Конфликты и гонки (проверено)

- **`concurrency` с деплоем.** `ci.yml` → группа `ci-${{ github.ref }}`,
  `deploy.yml` → `deploy-production`. Группы не пересекаются, взаимной отмены
  нет. Post-merge CI и деплой идут **параллельно**.
- **Post-merge CI НЕ гейтит деплой** — сознательно. Гейтить = +15-20 мин к
  каждому деплою. Это **детектор**, а не гейт: алерт прилетает уже по
  задеплоенному состоянию, и в теле issue это написано прямым текстом (решение
  — откат или хотфикс).
- **Частые мержи подряд.** `cancel-in-progress: true` на группе
  `ci-refs/heads/main`: следующий мерж отменяет незавершённый post-merge
  прогон. Промежуточный коммит остаётся невалидированным, но валидируется
  надмножество — актуальный main. Поэтому `cancelled` в алерте трактуется как
  «ничего не делать»: отменённый прогон ≠ красный main.
- **Рекурсии нет.** `ci.yml` больше вообще ничего не диспатчит: единственный
  диспатч живёт в `auto-merge-on-label.yml`, который работает на
  `pull_request: labeled` и в post-merge прогонах не участвует.
- **PR-путь не затронут.** Имена required-контекстов
  (`Typecheck · Lint · Unit Tests`, `E2E Tests`) не менялись; docs-only PR
  по-прежнему коротит через paths-filter.
- **Гонки «сквош → диспатч» нет — проверено фактами, не рассуждением.** Между
  `gh pr merge --squash` и `gh workflow run` теоретически возможна eventual
  consistency: диспатч мог бы подхватить предыдущий `main`. Замер (аудит
  2026-07-27): 98 наблюдений — 97 прогонов `deploy.yml` с 2026-06-27 плюс
  первый post-merge прогон CI — **0 расхождений** `headSha` с фактическим tip
  main на момент диспатча; медианный разрыв «коммит → диспатч» 3 сек. Стресс-
  участок 2026-07-13 (пять мерджей за ~7 минут, коммиты через 18–80 сек) —
  все пять диспатчей несли свой SHA. Формально вероятность >0, эмпирически за
  98 наблюдений ноль.
- **Диспатч с чужим `ref` не дотянется до PAT.** `post_merge_alert` — един-
  ственный job в `ci.yml` с секретом, поэтому он и гейтится по `inputs.ref`
  (`'' | 'main'`), и чекаутит строго `main`. Иначе `gh workflow run ci.yml
--ref main -f ref=<чужая-ветка>` проходил бы гард `github.ref == main` и
  исполнял чужой `post-merge-alert.sh` с телеметрийным PAT.

## 6. Диагностика

```bash
# Идут ли post-merge прогоны вообще
gh run list --branch main --workflow=ci.yml --limit 10

# Диспатчится ли CI после мержа (шаг "Dispatch post-merge CI on main")
gh run list --workflow=auto-merge-on-label.yml --limit 5

# Открытые алерты
gh issue list --repo yaremenko-maksym/cheekycheese-telemetry --label ci-main-broken --state open
gh issue list --label ci-main-broken --state open   # фолбэк-канал

# Ручной post-merge прогон
gh workflow run ci.yml --ref main
```

**Симптом: post-merge прогонов нет.** Проверить шаг `Dispatch post-merge CI on
main` в последнем `auto-merge-on-label` ране; он падает громко (без
`|| true`), так что молчаливой потери быть не должно.

**Симптом: прогон зелёный, но подозрительно быстрый.** Открыть Job Summary →
`### CI scope`. `work-steps enabled: false` на push/dispatch означает
регрессию в шаге `Resolve run scope`.
