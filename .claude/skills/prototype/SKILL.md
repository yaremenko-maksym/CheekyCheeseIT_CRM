# Прототип — одноразовый код, отвечающий на один вопрос

Наш `design-gate` знает три тира, и любой новый экран — Tier 1: генерация в Claude Design, spec,
fidelity-аудит по четырём классам устройств. Для **исследовательского** экрана, где ещё не решено,
каким он должен быть, это дорого и отвечает не на тот вопрос.

Прототип дешевле и отвечает на **один** вопрос. «Одноразовый» — ограничение на то, **как пишется**
код, а не обещание его удалить: проверенное решение переезжает в настоящий код.

## Первым делом — запиши вопрос

Одна строка в шапке прототипа: **на какой вопрос он отвечает**. Прототип без записанного вопроса
— не прототип, а черновик, который потом никто не сможет принять или отклонить.

Дальше выбери ветку. Ошибка ветки обесценивает всю работу:

| Вопрос                                            | Ветка      |
| ------------------------------------------------- | ---------- |
| «Как это должно выглядеть?»                       | **UI**     |
| «Правильная ли модель состояний / бизнес-логика?» | **Логика** |

Вопрос неоднозначен, владелец недоступен → бэкенд-модуль даёт логику, экран или компонент даёт UI;
допущение зафиксировать строкой в шапке (это A1 по `autonomy-levels.md`).

## Ветка UI — варианты на одном роуте

**Предпочитать существующий роут.** Вариант, который стоит внутри настоящей страницы — с реальным
хедером, сайдбаром, реальными данными и реальной плотностью — оценивается честно. Отдельный
пустой роут это вакуум, где любой вариант выглядит прилично.

- **Так (по умолчанию):** роут уже есть, варианты рендерятся на **том же** роуте под
  `?variant=`. Загрузка данных, параметры и авторизация остаются; меняется только отрисовка.
- **Иначе (крайний случай):** совсем новая поверхность, которую некуда встроить. Одноразовый роут
  по существующей конвенции роутинга TanStack Router, со словом `prototype` в пути.

Дальше:

1. **Три варианта по умолчанию**, максимум пять. Больше — уже не «радикально разные», а шум.
2. **Различаться структурой**, не цветом: другая раскладка, другая иерархия информации, другой
   главный affordance. Три слегка разные сетки карточек — это обои, а не прототип. Два варианта
   вышли похожими → переделать один с явным запретом на приём первого.
3. Собирать **нашими** компонентами (shadcn/ui) и токенами `globals.css` — иначе выбранный
   вариант не переносится и решение принято по картинке, которой не существует в проде.
4. **Переключатель** — плавающая панель снизу по центру: стрелка влево, метка варианта, стрелка
   вправо; стрелки клавиатуры тоже листают (кроме фокуса в `input` / `textarea` /
   `contenteditable`); обновляет search-параметр через роутер, чтобы ссылка была расшариваемой;
   **скрыт в прод-сборке** (`import.meta.env.PROD`), чтобы случайно смёрженный прототип не уехал
   пользователям.
5. **Скриншоты каждого варианта** на 375 и 1440 (`browser_resize` + `browser_take_screenshot`) —
   одним сообщением владельцу. Это и есть AFK-форма: три картинки, ответ одним словом.

Типичный ответ — «шапку из B, сайдбар из C». Это и есть искомый дизайн.

## Ветка логики — один HTML-файл

Один самодостаточный `.html`: ни сборки, ни сервера, ни фреймворка. Открывается двойным тапом,
переживает пересылку в мессенджер.

1. **Логика — чистым модулем** в одном `<script>`: редьюсер `(state, action) => state`,
   стейт-машина, набор чистых функций или класс — что честнее отвечает на вопрос. Никакого DOM
   внутри: страница зовёт модуль, обратно ничего не течёт. Именно это делает модуль переносимым в
   настоящий код после ответа.
2. **Язык домена, не кода.** Кнопки и поля состояния читаются словами из `CONTEXT.md`:
   «обязательство», «расчёт», «доля дропа», а не `PENDING_PAYOUT`, `settleByCompany`.
3. **Раскладка:** заголовок и вопрос → панель текущего состояния (подписанные поля, не дамп JSON),
   перерисовывается после каждого клика → кнопки свободной игры (по одной на действие) → вкладки
   сценариев: короткое описание ситуации и по кнопке на шаг, старт сбрасывает в известное начальное
   состояние.
4. **Сценарии — про неудобные случаи**: счастливый путь, каверзный край, попытка сделать то, что
   должно быть запрещено.

## Правила обеих веток

- **Никаких тестов.** Прототип, которому нужны тесты, уже не прототип.
- **Никакой реальной записи в БД.** Состояние в памяти. Если вопрос именно про персистентность —
  scratch-база с очевидным именем; живую `crm_db` не писать никогда (`live-db-access.md`).
- **Не обобщать.** «А вдруг потом понадобится X» — не понадобится: прототип отвечает на один вопрос.
- **Показывать состояние** после каждого действия или переключения варианта.
- **Тривиально запускается**: одна команда таск-раннера либо двойной клик.

## Когда получен ответ

1. Записать **ответ и вопрос**, на который он отвечает, в task-файл или тело PR. Ответ без
   вопроса через неделю нечитаем.
2. Проверенное решение (вариант / модуль логики) переносится в настоящий код — **переписанным
   как продакшн**, а не скопированным: прототип писался без обработки ошибок и тестов.
3. Сам прототип — **первоисточник**: коммит на выброшенную ветку `prototype/<name>` вне main,
   указатель на неё из задачи. В main не остаётся ни проигравших вариантов, ни переключателя:
   они гниют и путают следующего читателя.
4. Выбранный UI дальше идёт обычным путём `design-gate` — прототип отвечает «что», а не
   «достаточно ли хорошо сделано».
