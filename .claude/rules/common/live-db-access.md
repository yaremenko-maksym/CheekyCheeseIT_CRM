# Rule: Доступ к живой базе `crm_db` — чтение можно, запись нельзя

**Status:** Always-on
**Applies to:** Все агенты (Coder, AutoTest, DevOps, code-reviewer, security-reviewer, manual-qa, Master)
**Source:** Решение владельца 2026-08-22 по итогам инцидента-наблюдения (пункт бэклога 166):
security-reviewer подключился к `crm_db` на чтение, чтобы проверить находку, — и именно это дало
две HIGH-находки на PR #589, которые не ловил ни один тест.

---

## Почему правило переписано, а не ужесточено

Прежняя формулировка была абсолютной («к `crm_db` не подключаться **никогда**») и жила **только
в тексте промптов** — канонического файла не существовало, обрывки были в `git-policy.md`,
`light-track.md`, `agent-isolation.md`. Правило нарушали не из небрежности, а потому что
read-only доступ к реальным данным — единственный способ отличить настоящую находку от
гипотетической. Правило, которое нарушают ради полезной работы, воспитывает обход и обесценивает
себя целиком — тот же довод, по которому мы сузили стражей в PR #561.

Поэтому граница проведена там, где она содержательна: **не «подключаться / не подключаться», а
«читать / писать»**.

## The rule

| Операция                                                       | `crm_db`   |
| -------------------------------------------------------------- | ---------- |
| `SELECT`, `EXPLAIN`, чтение схемы                              | **можно**  |
| `INSERT` / `UPDATE` / `DELETE` / `TRUNCATE`                    | **нельзя** |
| DDL любого вида (`ALTER`, `CREATE`, `DROP`, миграции)          | **нельзя** |
| `db:push`, `db:seed`, `db:migrate`                             | **нельзя** |
| Запуск тестов, которые пишут (integration-спеки, E2E)          | **нельзя** |
| Поднятие dev-сервера с `DATABASE_URL`, указывающим на `crm_db` | **нельзя** |

**Пишущая работа — всегда на scratch/QA-базе**, `DATABASE_URL` задаётся **инлайном в самой
команде** (не `export` — экспорт живёт до конца сессии и воспроизводит ровно ту дыру, из-за
которой базу однажды затёрли).

## Обязательное подтверждение фактом

Перед первой командой к любой базе — подтвердить, куда подключился:

```sql
SELECT current_database(), version();
```

Причина не формальная: на порту 5432 на машине владельца уживаются **два разных Postgres**
(нативный Homebrew и docker-compose), и `localhost` резолвится в тот, которого не ждёшь.
Одноимённые базы в них — разные базы.

## Гигиена чтения

- Читать **точечно**: тот срез, что нужен выводу, а не «посмотрим, что там есть».
- **Персональные данные не тащить в отчёт.** Если для вывода нужны имена — агрегируй (счётчики,
  суммы) или обезличивай. В отчёте по #589 реальные ФИО сотрудников оказались в транскрипте без
  необходимости: для вывода «отчёт показывает всю популяцию» хватало числа.
- Результат чтения — **аргумент в ревью, а не источник правды для правки данных**. Нашёл
  расхождение в данных — готовь SQL для владельца, не чини сам.

## Что остаётся механически защищённым (и почему этого мало)

Уже существует и продолжает действовать:

- `apps/api/src/database/seed-db-guard.ts` — `db:seed` отказывается работать на базе, чьё имя не
  выглядит одноразовым (эскейп-хатч `SEED_CONFIRM_LIVE_DB_NAME` — только инлайном).
- `apps/api/src/test/integration-db-guard.ts` — то же для интеграционных спек.
- `.claude/hooks/pre-bash-live-db-guard.sh` — блокирует запуск dev-сервера против живой базы.

Все три ловят **разрушительные** операции. Обычный `psql` / `SELECT` не ловит ничто — и это
теперь **намеренно**, а не пробел: чтение разрешено.

## Связанные правила

- `.claude/rules/common/git-policy.md` — `DATABASE_URL=` (пустой) при push feature-веток.
- `.claude/rules/common/agent-isolation.md` — изоляция worktree и процессов.
- `.claude/rules/common/light-track.md` — scratch-базы при параллельной работе агентов.
